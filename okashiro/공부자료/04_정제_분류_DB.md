# 04. 정제·분류·DB (`build_db.py`, `categorize.py`)

수집한 CSV는 "쇼핑몰이 보여 준 그대로의 글자"입니다. 비교·정렬·검색을 하려면 정리가 필요합니다.
`build_db.py`가 CSV 3개를 읽어 정리하고 SQLite DB(`okashiro.db`)로 만듭니다. 실행할 때마다 **DB를 지우고 처음부터 새로 만듭니다**(`os.remove(DB_PATH)`).

## 1. 왜 CSV를 거치나
수집(느림, 실패 가능, 사이트 영향)과 정리(빠름, 내 PC 안)를 분리하기 위해서입니다.
- 정리 규칙을 고칠 때마다 사이트를 다시 긁을 필요가 없음 (CSV에서 몇 초면 DB 재생성)
- CSV는 원본 보관 역할: 정리가 틀려도 원문에서 다시 계산 가능
- 단점: 파일이 늘어남. 하지만 규모(수천 건)에서는 문제없음

## 2. 가격 문자열 → 숫자
```python
def parse_price(text):
    digits = re.sub(r'[^\d]', '', text or '')      # 숫자가 아닌 글자 전부 제거
    return int(digits) if digits else None
```
- "1,900원" → 1900. 'NoDiscount', 'NoSale'은 숫자가 없으니 None.
- **문자열 비교의 함정**: "10,000" < "9,000" (첫 글자 '1'이 '9'보다 작아서). 정렬·가격대 필터는 숫자여야 정확합니다.

가격 보정 규칙:
```python
sale = parse_price(row["할인가"]); orig = parse_price(row["정가"])
if sale is None: sale = orig            # 할인가 없으면 정가가 곧 판매가
if orig is None: orig = sale
if not sale or sale <= 0: bad_price += 1; continue   # 가격 없음/0원은 버림
if orig < sale: orig = sale             # 정가가 더 싼 이상 데이터 보정
pct = round((orig - sale) / orig * 100) # 할인율 %
```
쇼핑몰마다 "할인 없음"을 다르게 표현해서 한 규칙(정가=판매가, 할인율 0)으로 통일한 것입니다.

## 3. 중복 제거
```python
url = canon_url(site["key"], row["상품링크"])
if url in seen: dup += 1; continue
seen.add(url)
```
- 같은 상품이 여러 페이지·카테고리에 나올 수 있음 → **상품 주소 기준**으로 한 번만.
- `canon_url`: 엔핍은 주소에 정렬 조건 등이 붙어 달라질 수 있어 `it_id`만 남긴 표준 주소로 통일.
- DB 차원 보장: `UNIQUE(site, url)` 제약 → 같은 쇼핑몰의 같은 주소는 DB가 거부.

## 4. 과자가 아닌 상품 제외
```python
EXCLUDE_WORDS = ["롬앤", "라인삭스", "메쉬파우치"]       # categorize.py
if is_excluded(name): excluded += 1; continue
```
엔핍에 화장품·양말·파우치가 섞여 있었습니다. 서비스 목적(과자 비교)과 맞지 않아 이름 키워드로 제외.

## 5. 이미지 문제 두 가지와 보정
수집 단계의 약점을 DB 생성 단계에서 보정합니다.
1. **배지 이미지**: 엔핍은 목록의 첫 `<img>`가 BEST 배지인 경우가 있음 (이미지 주소에 `/data/badge/`)
   → 상품 페이지에서 `og:image`(공유용 대표 이미지)를 찾아 받음
   ```python
   m = re.search(r'<meta property="og:image" content="([^"]+)"', r.text)
   ```
2. **같은 이름, 다른 상품**: 수집 때 이미지를 `상품명.jpg`로 저장하니 이름이 같으면 덮어써짐
   → 이름이 같은데 이미지 주소가 다른 상품(`ambiguous_names`)은 자기 이미지 주소로 다시 받음
- 다시 받은 이미지는 `image_cache/`에 **상품 주소의 해시(md5)** 이름으로 보관. (DB id는 재생성 때마다 바뀔 수 있어서 id 대신 주소 기반 키 사용)
- 최종 이미지는 `static/images/사이트_ID.jpg`로 복사하고 DB에는 상대 경로만 저장.

## 6. 테이블 구조
```sql
CREATE TABLE products (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    site TEXT NOT NULL,            -- 'coco' / 'nppip' / 'iroiro'
    site_label TEXT NOT NULL,      -- 화면 표시용 한글 이름
    category TEXT,                 -- 쇼핑몰의 원래 분류
    main_category TEXT NOT NULL,   -- 우리가 붙인 공통 분류 (10개 중 하나)
    name TEXT NOT NULL,
    orig_price INTEGER NOT NULL,   -- 정가
    sale_price INTEGER NOT NULL,   -- 판매가
    discount_pct INTEGER NOT NULL, -- 할인율(%)
    image TEXT,                    -- 이미지 상대 경로 (없으면 NULL)
    url TEXT NOT NULL,             -- 쇼핑몰 상품 페이지
    name_norm TEXT NOT NULL,       -- 검색용: 공백 제거 + 소문자
    name_cho TEXT NOT NULL,        -- 검색용: 초성만
    UNIQUE(site, url)
)
```
`NOT NULL`은 "비어 있으면 안 된다"는 제약입니다. 가격이 없는 행은 위에서 이미 걸러 DB에 못 들어옵니다.

### 검색용 칼럼 미리 계산
```python
CHO = "ㄱㄲㄴㄷㄸㄹㅁㅂㅃㅅㅆㅇㅈㅉㅊㅋㅌㅍㅎ"
def to_initials(text):
    out = []
    for ch in text:
        code = ord(ch) - 0xAC00                 # 한글 음절은 유니코드 0xAC00부터 시작
        out.append(CHO[code // 588] if 0 <= code <= 11171 else ch)
    return "".join(out)
```
- 한글 한 글자 = 초성(19) × 중성(21) × 종성(28)의 조합이라 `(글자코드 - 0xAC00) // 588`이 초성 번호 (588 = 21×28).
- "곤약젤리" → "ㄱㅇㅈㄹ". 한글이 아닌 글자(영문·숫자)는 그대로 둠.
- **저장 시 한 번만 계산** → 검색할 때는 `LIKE`로 바로 찾음 (매 검색마다 전체 상품을 변환하지 않음).
- `normalize`: 공백 제거 + 소문자. "Kit Kat"과 "kitkat"을 같게 취급.

## 7. 분류 — `categorize.py` (키워드 규칙)
사이트마다 분류 체계가 다릅니다(어떤 곳은 분류가 아예 없음). 화면에서 같은 기준으로 필터하려면 **공통 분류 10개**가 필요합니다.
`과자·스낵, 초콜릿, 사탕·젤리, 쿠키·디저트, 견과·건어물, 라면·면류, 음료·차, 소스·조미료, 식사·즉석식품, 기타`

### 동작 방식
1. **직접 지정(MANUAL)**: 사람이 확인해서 정한 상품은 규칙보다 우선.
2. **이름 정리 `clean()`**: 유통기한 표기, "맛" 표현("녹차맛")은 상품 종류가 아니라 향이므로 제거. 맛이 종류로 오인되는 것을 막음.
3. **키워드 검색**: 분류마다 키워드 목록(`RULES`)이 있고, 이름에서 **가장 뒤에 나오는 키워드**의 분류를 선택.
   - 이유: 종류는 이름 끝에 오는 경우가 많음. "초콜릿 커버 비스킷" → '초콜릿'(앞), '비스킷'(뒤) → 뒤가 이김 → 쿠키·디저트.
   - 동점이면 앞 분류가 이김.
4. 키워드가 없으면: "과자"라는 일반 단어 → 과자·스낵 / 쇼핑몰의 원래 분류(`SOURCE_FALLBACK`) / 사이트 기본값(`SITE_FALLBACK`: 코코재팬은 과자·스낵) / 그래도 없으면 기타.

5,585건 중 '기타' 2건(스피루리나, 아트시트).

### 왜 머신러닝이 아닌가
| 대안 | 거부 이유 |
|---|---|
| 머신러닝 분류 | 학습에 필요한 **정답 라벨이 없음**. 만들려면 수천 건을 손으로 달아야 함. 오분류 원인을 설명하기 어려움. |
| 쇼핑몰 원본 분류 사용 | 사이트마다 기준이 다르고 일부 사이트는 분류가 없음 |
| 키워드 규칙 (선택) | 즉시 동작, 틀리면 키워드만 고치면 됨(원인 설명 가능). 한계: 새 상품명에는 규칙 추가 필요 |

### 겪은 오류: 넓은 키워드의 부작용
키워드를 늘려 '기타'를 줄이는 과정에서 `우니`, `이카`, `콘부`, `명란`, `연어`, `포타주`, `아이스`, `드라이`, `옥수수`, `고보`, `스콘`, `마로`처럼 **다른 단어의 일부로 자주 등장하는 짧은 키워드**가 엉뚱한 상품을 끌어와 오분류가 늘었습니다.
→ 분류 결과를 확인하며 해당 키워드를 삭제하고 더 구체적인 단어로 교체. 규칙을 추가할 때마다 결과를 확인해야 하는 이유입니다.

## 8. 동일 상품을 묶지 않은 이유
"같은 과자가 쇼핑몰마다 얼마인가"를 보려면 상품 매칭이 필요해 보이지만, **이름 유사도로 자동으로 묶는 것은 하지 않았습니다.**
- 표기가 쇼핑몰마다 다름(번역투, 용량 표기, 브랜드 표기) → 다른 상품끼리 묶이거나 같은 상품이 안 묶일 수 있음
- 잘못 묶으면 "이게 최저가"라는 **틀린 정보**를 줌
- 그래서 사용자가 검색한 뒤 **판매가순으로 정렬해서 직접 비교**하게 함. 최저가를 자동 추천하지 않고 선택은 사용자에게.

## 9. SQL 기초 (이 프로젝트에서 쓴 것)
```sql
-- 저장
INSERT INTO products (site, name, sale_price, ...) VALUES (?, ?, ?, ...);

-- 조회
SELECT name, sale_price, discount_pct, url
FROM products
WHERE name_cho LIKE ?        -- 이름/초성 검색
  AND site IN (?, ?)         -- 쇼핑몰
  AND sale_price <= ?        -- 가격대
ORDER BY discount_pct DESC   -- 정렬
LIMIT 40 OFFSET 0;           -- 40개씩, 0번째부터
```
- `?` **파라미터 바인딩**: 값을 SQL 문장에 직접 이어붙이지 않고 따로 전달. 검색어에 `'; DROP TABLE...` 같은 SQL이 들어와도 **그냥 글자**로 취급됨(SQL 주입 방지).
- `LIKE '%단어%'`: 단어를 포함하는 행. `%`는 임의의 글자 여러 개.
- `LIMIT 40 OFFSET 80`: 80개 건너뛰고 40개 → 3페이지.
- `UNIQUE(site, url)`, `NOT NULL`: DB 차원에서 데이터 품질을 지킴.

## 10. 왜 SQLite인가
| 대안 | 판단 |
|---|---|
| PostgreSQL / MySQL | 서버 설치·계정·운영 필요. 읽기 위주 수천 건에는 과함. 이용자가 늘면 전환 대상. |
| CSV 직접 조회 | 검색·정렬·필터를 매번 직접 구현해야 하고 느림 |
| **SQLite** | 설치 불필요, DB가 파일 하나, 파이썬 기본 내장. 읽기 위주 서비스에 충분 |

한계: 동시에 쓰는 사용자가 많아지면 약함. 이 서비스는 **읽기 전용**이라 문제가 적습니다(연결도 `mode=ro`).
또 다른 한계: 매번 DB를 새로 만들어서 **가격 이력이 남지 않음** → 가격 변동 추적 불가. 이력이 필요하면 수집 날짜 칼럼이나 이력 테이블을 설계에 넣어야 합니다.
