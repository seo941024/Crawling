|---|---|---|

  - BeautifulSoup: 받은 HTML에서 원하는 부분(상품명, 가격)만 골라내는 도구
  - Selenium: 실제 크롬 브라우저를 프로그램으로 띄워서 조종하는 도구

- **활용 도구**: 코드에 넣는 게 아니라 개발할 때 쓰는 프로그램이나 서비스입니다.

## 5장 서비스 시연 (1분 5초, 영상)

### 이 장 이해하기
- **JSON**: 데이터를 주고받을 때 쓰는 글 형식. 예: `{"name": "킷캣", "price": 1900}`
- **API**: 화면 없이 데이터만 주는 주소. 예: `/api/search?q=킷캣`으로 요청하면 상품 목록이 JSON으로 옵니다.
- **fetch**: JavaScript가 페이지를 새로 열지 않고 API에 데이터를 요청하는 기능
- 왜 나눴나? 필터를 바꿀 때마다 페이지 전체를 새로 받으면 느리고 화면이 깜빡입니다. 데이터만 받아서 목록 부분만 바꾸면 빠릅니다.
- **textContent**: 화면에 글자를 넣는 방법입니다.
  - 다른 방법인 `innerHTML`은 넣은 글자를 HTML(코드)로 해석합니다. 그래서 상품명에 `<script>나쁜코드</script>` 같은 게 섞여 있으면 그 코드가 실행될 수 있습니다.
  - `textContent`는 무엇이 들어 있든 **그냥 글자로만** 보여 줍니다.
  - 상품명은 남의 사이트에서 가져온 값이라 믿을 수 없기 때문에 textContent를 썼습니다.

### 말할 대본
완성된 서비스입니다.
(영상 중) 상품을 이름이나 초성으로 검색하고, 분류, 가격대, 할인율, 쇼핑몰로 좁힌 뒤 가격순으로 정렬합니다. 상품을 누르면 해당 쇼핑몰의 상품 페이지가 새 탭으로 열립니다.
화면 구조에서 두 가지를 신경 썼습니다. 첫째, 필터를 바꿀 때마다 페이지 전체를 다시 받으면 느리기 때문에, Flask는 상품 데이터만 JSON으로 보내고 JavaScript가 목록만 새로 그리게 했습니다. 둘째, 상품명은 외부 사이트에서 가져온 값이라 스크립트가 섞여 있으면 실행될 위험이 있어서, 글자로만 출력하는 textContent를 썼습니다.

## 6장 데이터 파이프라인과 기술 스택 (50초)

### 이 장 이해하기
- **파이프라인**: 앞 단계의 결과가 다음 단계의 재료가 되는 흐름. 수집 → 검증·정제 → 저장·서비스
- **정적 사이트 / 동적 사이트** (7장에서 자세히)
  - 정적: 서버가 상품이 이미 들어 있는 완성된 HTML을 보냄 → requests로 받기만 하면 됨
  - 동적: 서버는 빈 틀만 보내고, 브라우저에서 JavaScript가 상품을 나중에 채움 → 실제 브라우저(Selenium)로 열어야 상품이 보임
  - **렌더링**: 브라우저가 HTML과 JavaScript를 실행해서 화면을 완성하는 것
- **정규식**: 글자에서 원하는 패턴만 찾는 규칙. 여기서는 "1,900원"에서 숫자만 남기는 데 씀
- **UNIQUE 제약**: DB에 "같은 값은 두 번 저장 금지"라고 걸어 두는 규칙
- **정답 라벨**: 머신러닝이 배우려면 "이 상품은 과자" 같은 정답이 달린 예시가 많이 필요합니다. 그게 없어서 머신러닝 대신 키워드 규칙을 썼습니다.
- **예약 수집**: GitHub Actions가 매주 정해진 시간에 수집 코드를 자동으로 돌림

### 말할 대본
전체 구조입니다. 단계마다 풀어야 할 문제가 달라서 기술도 단계별로 골랐습니다. 수집은 사이트마다 상품을 보내는 방식이 달라서 requests와 Selenium을 나눠 썼습니다. 검증·정제는 가격이 문자열이고 분류 기준이 제각각이라서 정규식과 키워드 규칙을 썼습니다. 저장과 서비스는 서버 설치가 필요 없는 SQLite와, 구조를 직접 설계할 수 있는 Flask를 썼고, GitHub Actions로 매주 자동 수집합니다. 이어서 단계별로 어떤 문제를 어떻게 풀었는지 말씀드리겠습니다.

## 7장 수집 도구 선택 (1분 10초)

### 이 장 이해하기
- **판별 방법**: 같은 페이지를 두 번 받아 봅니다.
  - requests로 받은 HTML에서 상품 개수 세기
  - Selenium(브라우저)으로 연 HTML에서 상품 개수 세기
  - 둘이 같으면 정적, requests 쪽이 0개면 동적입니다. 엔핍은 수집 당시 requests 0개, Selenium 20개라서 동적으로 판정했습니다.
- **오른쪽 코드 사진의 의미**: 판별 결과대로 코드를 다르게 짠 증거입니다.
  - 정적(코코재팬): `requests`로 받은 응답을 바로 BeautifulSoup으로 분석
  - 동적(엔핍): `driver.get`으로 브라우저를 열고, `time.sleep(3)`으로 3초 기다려 상품이 채워지게 한 뒤, 완성된 HTML(`page_source`)을 분석
- **개발자도구(F12)**: 브라우저에서 F12를 누르면 페이지의 HTML 구조를 볼 수 있습니다. 상품 하나가 어떤 태그(`li`, `div`)와 이름표(class)로 되어 있는지 보고, 그 단위로 뽑았습니다.
- **페이지 이동 방식**: 다음 페이지로 넘어가는 주소 규칙이 사이트마다 다릅니다.
  - `?page=2`처럼 주소 뒤에 번호를 붙이는 방식
  - `/page/2/`처럼 경로에 번호를 넣는 방식
  - 코코재팬의 '더보기' 버튼(AJAX): 버튼을 누르면 페이지 이동 없이 숨은 주소로 데이터를 받아 옵니다. 개발자도구의 네트워크 탭에서 그 숨은 주소를 찾아 직접 요청했습니다.

### 말할 대본
수집 단계의 첫 번째 문제는 사이트마다 상품을 보내는 방식이 다르다는 점이었습니다. 서버가 완성된 HTML을 보내는 정적 사이트는 requests로 받으면 되지만, JavaScript가 상품을 나중에 채우는 동적 사이트는 requests로 받으면 빈 틀만 옵니다. 반대로 정적 사이트에 Selenium을 쓰면 브라우저를 띄우느라 느리고 무겁습니다.
그래서 같은 페이지를 두 방식으로 받아 상품 개수로 판별했습니다. 엔핍은 수집 당시 requests로 0개, Selenium으로 20개가 나와서 Selenium을 썼고, 오른쪽 코드처럼 브라우저가 상품을 채울 때까지 기다린 뒤 분석했습니다.
상품 추출은 개발자도구로 상품 하나의 태그와 클래스 구조를 분석해서 그 단위로 뽑았고, 코코재팬의 더보기 버튼은 네트워크 탭에서 숨은 데이터 주소를 찾아 직접 요청했습니다.

### 질문이 나오면
- **지금은 엔핍도 requests로 되던데요?** 이후 다시 확인했을 때는 requests로도 20개가 잡혔습니다. 사이트가 바뀐 것인지는 규명하지 못했고, 그래서 판별을 같은 방법으로 다시 확인할 수 있게 정리해 두었습니다.

## 8장 수집 허용 범위 확인 (50초)

### 이 장 이해하기
- **상태코드**: 서버가 응답과 함께 주는 숫자. 200은 정상, 403은 접근 거부, 404는 페이지 없음.
  - 200은 "접속이 된다"는 뜻일 뿐, "가져가도 된다"는 허락이 아닙니다.
- **robots.txt**: 사이트 운영자가 "프로그램(크롤러)은 여기까지만 들어와도 된다"고 적어 둔 안내 파일. `사이트주소/robots.txt`로 볼 수 있습니다.
  - `Disallow: /` → 사이트 전체 접근 금지
  - 법으로 강제되지는 않지만 운영자의 의사 표시라서 따랐습니다.
- **파싱**: 글을 읽어서 의미 단위로 나누는 것. robots.txt를 파이썬이 이해할 수 있게 읽는 것.
- **can_fetch()**: 파이썬 기능. "이 주소에 들어가도 되나?"를 물으면 True(허용) 또는 False(금지)로 답합니다.
- **활용**: 수집 코드가 돌기 전에 이 확인을 먼저 자동으로 하고, 금지면 수집을 멈추게 만들었습니다.
- **이용약관**: 사이트 이용 규칙. 정보를 복제해서 다른 곳에 제공하는 것을 제한하고 있어서, 인터넷에 공개하지 않고 내 컴퓨터에서만 시연합니다.

### 말할 대본
두 번째 문제는 수집해도 되는 사이트인지였습니다. 처음에는 상태코드 200, 즉 접속이 되는지만 봤는데, 접속이 되는 것과 수집이 허용되는 것은 다릅니다. 운영자는 robots.txt로 크롤러의 접근 범위를 알리기 때문에, 이 파일을 읽어 수집할 주소마다 can_fetch로 허용 여부를 판단했습니다. 그 결과 재팬푸드몰은 사이트 전체가 금지여서 서비스에서 제외했습니다. 그리고 이 확인을 매번 수집 전에 자동으로 하게 해서, 허용되지 않으면 수집이 멈추도록 했습니다. 이용약관에도 정보 제공 제한이 있어서 공개 배포 대신 로컬에서 시연합니다.

## 9장 수집 종료 조건과 접근 차단 대응 (1분 30초)

### 이 장 이해하기
- **① 코코재팬 일부 누락**
  - 수집 코드에 "10페이지까지 수집"처럼 페이지 수를 고정해 뒀는데, 실제 페이지는 더 많아서 뒤쪽이 빠졌습니다.
  - **종료 조건**: 수집을 언제 멈출지 정하는 규칙. 고정 숫자 대신 "새 상품이 더 안 나오면 멈춤"으로 바꿨습니다.
  - **CSV**: 표 데이터를 쉼표로 구분해 저장하는 파일. 수집 도중 실패해도 기존 CSV가 망가지지 않게, 임시 파일에 먼저 쓰고 성공했을 때만 바꿔 끼웠습니다.
- **② 이로이로도쿄 반복 수집**
  - **리다이렉트**: 요청한 주소가 아니라 다른 주소로 자동으로 보내 버리는 것. 없는 페이지를 요청하면 오류 대신 다른 페이지로 보내서, 같은 상품이 계속 수집됐습니다.
  - 상태코드는 계속 200이라 오류로 알 수 없었습니다.
  - **res.url**: 실제로 도착한 주소. 요청한 주소와 다르면 "끝까지 왔다"고 보고 멈췄습니다.
- **③ GitHub Actions에서만 403**
  - 내 컴퓨터에서는 되는데 GitHub 서버에서 돌리면 코코재팬이 접근 거부(403)했습니다.
  - **User-Agent**: 요청에 붙는 "나는 어떤 브라우저다"라는 자기소개. 이걸 바꿔도 내 컴퓨터에서는 다 정상이라, 요청 내용이 원인이 아니었습니다.
  - **응답 헤더**: 응답에 붙어 오는 부가 정보. 거기에 `cf-mitigated: challenge`가 있었는데, 이는 **Cloudflare**(사이트 앞에서 봇을 막는 보안 서비스)가 "자동화 같으니 확인하겠다"고 막은 표시입니다.
  - 운영자가 막으려고 둔 장치라서 뚫지(우회하지) 않고, 코코재팬만 내 컴퓨터에서 수집한 데이터를 씁니다.

### 말할 대본
수집 중에 생긴 문제 세 가지와 원인을 좁힌 과정입니다.
첫째, 코코재팬 상품이 일부만 저장됐습니다. 오류 없이 끝나서 수집 범위를 의심했고, 시험 수집으로 세어 보니 실제 페이지가 제가 고정한 페이지 수보다 많았습니다. 고정값은 사이트가 바뀌면 다시 틀리므로, 새 상품이 없으면 끝나는 종료 조건으로 바꿨고, 실패해도 기존 데이터가 남도록 성공했을 때만 파일을 교체하게 했습니다.
둘째, 이로이로도쿄에서는 같은 상품이 반복 수집됐습니다. 상태코드는 계속 200이었고, 실제 도착한 주소를 보니 마지막 페이지 다음부터 다른 페이지로 보내지고 있었습니다. 그래서 요청한 주소와 도착한 주소가 다르면 끝내도록 했습니다.
셋째, GitHub Actions에서만 코코재팬이 403으로 막혔습니다. User-Agent를 바꿔 시험해도 제 PC에서는 모두 정상이라, 차단 응답의 헤더를 기록해 확인했고 Cloudflare의 봇 확인이었습니다. 운영자가 둔 장치라 우회하지 않고, 코코재팬만 PC에서 수집한 데이터를 씁니다.

### 질문이 나오면
- **왜 GitHub 서버만 막혔나요?** 요청 내용이 아니라 요청이 나온 곳의 차이로 보고 있지만, 정확한 이유는 규명하지 못했습니다.

## 10장 정제와 분류 (1분)

### 이 장 이해하기
- **가격 문자열 문제**: 수집한 가격은 '1,900원'처럼 **글자**입니다. 글자는 앞 글자부터 비교해서 정렬하기 때문에 '10,000원'이 '9,000원'보다 앞에 옵니다('1'이 '9'보다 작으니까). 숫자로 바꿔야 가격순 정렬과 가격대 필터가 맞습니다.
- **정규식 기반 숫자 추출**: '1,900원'에서 숫자가 아닌 것(쉼표, '원')을 지우면 1900만 남습니다.
- **UNIQUE(site, url)**: "같은 쇼핑몰의 같은 상품 주소는 한 번만 저장"하는 DB 규칙입니다.
- **키워드 분류**: 상품 이름에 '젤리'가 있으면 사탕·젤리, '라멘'이 있으면 라면·면류처럼 단어로 분류를 붙입니다.
  - 머신러닝을 안 쓴 이유: 배울 정답 예시가 없고, 틀렸을 때 왜 틀렸는지 설명하기 어렵습니다. 키워드 규칙은 틀리면 어떤 단어 때문인지 바로 보입니다.
- **가장 뒤쪽 키워드 우선**: "초콜릿 커버 비스킷"처럼 상품 종류는 보통 이름 끝에 옵니다. 그래서 뒤에 나온 '비스킷'을 기준으로 분류합니다.
- **오른쪽 코드**: 위는 이름에서 가장 뒤에 나온 키워드를 찾는 코드(`rfind`는 뒤에서부터 찾기), 아래는 가격에서 숫자만 남기는 코드입니다.

### 말할 대본
검증·정제 단계의 문제는 모은 데이터를 그대로는 비교할 수 없다는 점이었습니다. 가격은 '1,900원' 같은 글자라서 그대로 정렬하면 '10,000원'이 '9,000원'보다 앞에 옵니다. 그래서 정규식으로 숫자만 남겨 정수로 바꿨습니다. 같은 상품이 반복 저장되는 것은 쇼핑몰과 상품 주소 조합에 UNIQUE 제약을 걸어 DB에서 막았습니다.
분류는 사이트마다 없거나 기준이 달라서, 상품 이름의 키워드로 공통 분류 10개를 붙였습니다. 머신러닝은 학습할 정답 데이터가 없고 틀린 이유를 설명하기 어려워서, 원인을 바로 찾을 수 있는 키워드 규칙을 택했습니다. 상품 종류는 이름 끝에 오는 경우가 많아서 가장 뒤에 나온 키워드를 우선합니다.

### 질문이 나오면
- **새 상품명이 들어오면요?** 키워드가 없는 상품은 규칙을 추가해야 합니다. 대신 어떤 규칙을 추가하면 되는지가 바로 보입니다.

## 11장 저장과 조회 쿼리 (55초)

### 이 장 이해하기
- **쿼리**: DB에 보내는 명령문. SQL이라는 언어로 씁니다.
  - 예: `SELECT * FROM products WHERE name LIKE '%킷캣%'` = "상품 표에서 이름에 킷캣이 들어간 것 다 줘"
- **SQL 주입 (값 전달 칸)**
  - 검색어를 명령문에 **그대로 이어 붙이면** 문제가 생깁니다.
  - 사용자가 검색창에 `킷캣` 대신 `'; DROP TABLE products; --` 같은 글자를 넣으면, 이 글자가 명령문의 일부가 되어 "상품 표를 지워라"라는 명령으로 **실행**될 수 있습니다. 이것이 SQL 주입 공격입니다.
  - 비유: 주문서 양식에 "메뉴: ____" 칸이 있는데, 손님이 "김밥, 그리고 금고 열어 줘"라고 써서 직원이 그대로 따르는 상황입니다.
- **? 파라미터 바인딩 (해결 방법)**
  - 명령문에는 자리만 `?`로 비워 두고, 검색어는 **따로** 넘깁니다.
  - 예: `WHERE name LIKE ?` + 값 `'%킷캣%'`
  - DB는 `?` 자리에 들어온 것을 무조건 **값(글자)**으로만 취급합니다. 그래서 검색어에 명령처럼 생긴 글자가 있어도 실행되지 않고, 그냥 그런 이름의 상품을 찾을 뿐입니다.
  - 비유: 주문서의 메뉴 칸에 무엇을 쓰든 "메뉴 이름"으로만 읽는 규칙입니다.
- **정렬 칸 (ORDER BY에 ? 불가)**
  - "가격순", "할인율순" 같은 정렬 기준은 값이 아니라 명령문의 일부라서 `?`를 쓸 수 없습니다.
  - 그래서 미리 정해 둔 목록(가격 낮은 순, 할인율 순 등)에 있는 것만 고를 수 있게 했습니다. 목록에 없는 값이 오면 기본값을 씁니다.
- **초성 검색 칸**
  - 'ㄱㅇㅈㄹ'로 '고양이젤리'를 찾으려면 상품명의 초성이 필요합니다.
  - 검색할 때마다 5천 개 상품의 초성을 계산하면 느리니까, 저장할 때 한 번 계산해서 초성 칸(칼럼)에 넣어 두었습니다.
- **DB 칸**: SQLite는 파일 하나라 서버 프로그램을 따로 설치할 필요가 없습니다. 이 서비스는 읽기만 하고 데이터가 크지 않아서 충분합니다.
- **오른쪽 코드**: `?`로 값을 넘기는 부분, 초성 칸을 고르는 부분, 읽기 전용(`mode=ro`)으로 DB를 여는 부분(웹에서 DB를 바꾸지 못하게), 정렬을 목록에서만 고르는 부분입니다.

### 말할 대본
저장·서비스 단계에서는 안전하고 빠른 조회를 신경 썼습니다. DB는 읽기 위주의 작은 규모라서 서버 설치가 필요 없는 SQLite를 골랐습니다.
조회할 때 검색어를 명령문에 그대로 이어 붙이면, 검색어에 SQL 명령을 섞어 DB를 조작하는 SQL 주입이 가능합니다. 그래서 명령문에는 물음표로 자리만 두고 검색어는 따로 전달해, 항상 값으로만 처리되게 했습니다. 정렬 기준은 물음표를 쓸 수 없는 자리라서 정해 둔 목록에서만 고르게 했고, DB도 읽기 전용으로 열었습니다.
초성 검색은 검색마다 계산하면 느리기 때문에, 저장할 때 한 번 계산해서 초성 칼럼에 넣어 두었습니다.

### 질문이 나오면
- **데이터가 많아지면요?** 동시에 쓰는 이용자가 많아지면 PostgreSQL 같은 서버형 DB로 옮겨야 합니다.

## 12장 배운 점 (55초)

### 이 장 이해하기
- 표는 **겪은 일 → 배운 점 → 다음 프로젝트에서 처음부터 할 것** 순서입니다. 앞의 8장, 9장, 11장에서 실제로 겪은 일과 이어집니다.
- **가격 이력**: 지금은 수집할 때마다 DB를 새로 만들어서 지난주 가격이 사라집니다. 가격이 언제 올랐는지 같은 정보를 남기려면 수집 날짜를 함께 저장하는 표(이력 테이블)가 필요합니다.

### 말할 대본
마지막으로 배운 점과 다음 프로젝트에서 처음부터 다르게 할 점입니다.
첫째, robots.txt 확인을 수집 후에 했습니다. 다음에는 코드를 쓰기 전에 robots.txt와 이용약관부터 확인하겠습니다.
둘째, 페이지 수를 고정해서 누락과 반복 수집이 생겼습니다. 사이트의 끝은 고정값이 아니라 응답으로 판단해야 하므로, 종료 조건과 수집 건수 검증을 처음부터 설계하겠습니다.
셋째, 가격 비교 서비스인데 가격 이력을 남기지 못했습니다. 다음에는 이력 테이블을 설계 단계에 넣겠습니다.
정리하면 저는 문제가 생겼을 때 추측하지 않고 원인을 좁혀 확인하고, 아는 지식을 근거로 방법을 고르는 방식으로 이 서비스를 만들었습니다. 감사합니다.
