## 4장 서비스 시연 (1분 5초, 영상)

### 이 장 이해하기
- **JSON**: 데이터를 주고받는 글 형식. 예: `{"name": "킷캣", "sale_price": 1900}`
- **fetch**: JavaScript가 페이지를 새로 열지 않고 서버에 데이터만 요청하는 기능
- **textContent**: 화면에 글자를 **글자로만** 넣는 방법. 상품명에 `<script>`가 섞여 있어도 실행되지 않음 (`innerHTML`은 코드로 해석)

### 말할 대본
완성된 서비스를 영상으로 보여드리겠습니다.
(영상 중) 상품을 이름이나 초성으로 검색하고, 분류, 가격대, 할인율, 쇼핑몰로 좁힌 뒤 가격순으로 정렬해 쇼핑몰 간 가격을 비교합니다. 상품을 누르면 해당 쇼핑몰의 상품 페이지가 새 탭으로 열립니다.
화면 구조에서는 두 가지를 신경 썼습니다. 필터를 바꿀 때마다 페이지 전체를 다시 받으면 느리기 때문에, Flask는 상품 데이터만 JSON으로 보내고 JavaScript가 fetch로 받아 목록만 새로 그리게 했습니다. 그리고 상품명은 외부 사이트에서 가져온 값이라, 스크립트가 섞여 있어도 실행되지 않도록 글자로만 출력하는 textContent를 썼습니다.

## 5장 데이터 파이프라인과 기술 스택 (1분)

### 이 장 이해하기
- 단계마다 **사용 기술 → 역할(어디에 썼나) → 선정 근거(왜 골랐나)** 순서입니다. 대본은 선정 근거 위주로 말하고, 역할은 화면으로 보여 줍니다.
- **정적 사이트**: 서버가 상품이 들어 있는 완성된 HTML을 보냄 → requests로 충분
- **동적 사이트**: 서버는 빈 틀만 보내고 브라우저의 JavaScript가 상품을 채움 → Selenium으로 브라우저를 띄워야 함
- **정답 라벨**: 머신러닝이 배우려면 "이 상품은 과자" 같은 정답이 달린 예시가 많이 필요함
- **예약 수집**: GitHub Actions가 매주 일요일 새벽 3시(한국 시간)에 수집 코드를 자동 실행

### 말할 대본
전체 구조입니다. 쇼핑몰 세 곳의 상품 데이터를 수집하고, 비교할 수 있게 정제한 뒤, DB로 만들어 검색 서비스로 제공하는 흐름입니다. 단계마다 풀어야 할 문제가 달라서 기술도 단계별로 골랐습니다.
수집은 완성된 HTML을 보내는 정적 사이트는 requests만으로 빠르게, JavaScript가 상품을 나중에 만드는 동적 사이트는 Selenium으로 렌더링한 뒤 수집했습니다.
정제는 머신러닝을 학습시킬 정답 라벨이 없어서, 잘못 분류됐을 때 원인 규칙을 바로 찾아 고칠 수 있는 키워드 규칙을 택했습니다.
DB는 읽기 위주의 작은 규모라 서버 설치가 필요 없는 SQLite를, 서비스는 검색 결과를 JSON으로 주는 API를 직접 설계해 화면과 데이터를 나누려고 Flask를 썼고, GitHub Actions로 매주 자동 수집합니다.
이어서 단계별로 어떤 판단을 했는지 말씀드리겠습니다.

## 6장 수집 도구 선택 (1분 10초)

### 이 장 이해하기
- **표**: 다섯 사이트의 유형, 사용 기술, 페이지 이동 방식
  - 서비스에 쓰는 곳: 코코재팬, 이로이로도쿄, 엔핍 / 수집했지만 제외: 재팬푸드몰(robots.txt 금지), 구루메상(품절·더미 상품이 많은 사실상 운영 중단 사이트)
  - 코코재팬 '더보기'(AJAX): 페이지 이동 없이 숨은 주소로 데이터를 받아 옴. 개발자도구 네트워크 탭에서 그 주소를 찾아 직접 요청
- **판별 방법**: 같은 페이지를 requests와 Selenium으로 각각 받아 상품 개수를 비교. requests 쪽에 상품이 없으면 동적
- **왼쪽 아래 F12 캡처**: 코코재팬 상품 카드 하나의 HTML. 빨간 박스는 `li.sct_li`(카드 하나), `sct_txt`(상품명), `coco2-was`·`coco2-now`(정가·할인가)
- **오른쪽 코드**: 위는 코코재팬(받은 HTML `res.text`를 바로 분석), 아래는 엔핍(브라우저로 열고 3초 기다린 뒤 완성된 `page_source`를 분석). 상품 카드를 찾는 마지막 줄은 두 사이트가 같음

### 말할 대본
수집 단계의 첫 번째 문제는 사이트마다 상품을 보내는 방식이 다르다는 점이었습니다. 정적 사이트는 requests로 받으면 되지만, 동적 사이트는 requests로 받으면 빈 틀만 옵니다. 반대로 정적 사이트에 Selenium을 쓰면 브라우저를 띄우느라 느리고 무겁습니다.
그래서 같은 페이지를 두 방식으로 받아 상품 개수를 비교해 판별했고, 엔핍만 동적이라 Selenium을 썼습니다. 오른쪽 코드처럼 코코재팬은 받은 HTML을 바로 분석하고, 엔핍은 브라우저가 상품을 채울 때까지 기다린 뒤 분석합니다.
상품은 왼쪽 아래처럼 개발자도구로 상품 카드 하나의 태그와 클래스를 분석해서, 카드 단위로 찾고 그 안에서 상품명과 가격을 꺼냈습니다. 페이지 이동 방식도 사이트마다 달라서 각각 분석했고, 코코재팬의 더보기 버튼은 네트워크 탭에서 내부 데이터 주소를 찾아 직접 요청했습니다.
표의 다섯 곳 중 재팬푸드몰과 구루메상은 수집했지만 서비스에서는 제외했습니다.

### 질문이 나오면
- **판별 결과는 구체적으로?** 엔핍은 수집 당시 requests로 상품 0개, Selenium으로 20개였습니다. 이후 다시 확인했을 때는 requests로도 20개가 잡혔고, 사이트가 바뀐 것인지는 규명하지 못했습니다.
- **어떤 구조로 가져왔나요?** 상품 하나를 감싸는 반복 태그(코코재팬 `li.sct_li`, 엔핍 `div.item-row`, 이로이로도쿄 `div.type-product`)를 `find_all`로 전부 찾고, 카드 안에서 상품명·정가·할인가·이미지·링크를 꺼내 다섯 칸 CSV로 저장했습니다.
- **3초는 왜?** ★ 지수 답. 예: "상품이 채워지는 시간을 보고 여유 있게 잡았습니다. 더 정확하게는 요소가 나타날 때까지 기다리는 WebDriverWait를 쓸 수 있습니다."

## 7장 수집 허용 범위 확인 (40초)

### 이 장 이해하기
- **상태코드 200**: "접속이 된다"는 뜻일 뿐, "가져가도 된다"는 허락이 아님
- **robots.txt**: 운영자가 "크롤러는 여기까지만"이라고 적어 둔 파일. `Disallow: /`는 사이트 전체 금지
- **can_fetch()**: "이 주소에 들어가도 되나?"를 물으면 True/False로 답하는 파이썬 기능
- 표 첫 줄 **수집 근거**는 "처음에는 접속 가능(200)만 보고 수집했다, 하지만 접속 가능 ≠ 수집 허용"이라는 뜻입니다.
- 오른쪽 위는 `check_robots.py` 코드, 아래는 재팬푸드몰 robots.txt 화면

### 말할 대본
두 번째 문제는 수집해도 되는 사이트인지였습니다. 처음에는 상태코드 200, 즉 접속이 되는지만 봤는데, 접속이 되는 것과 수집이 허용되는 것은 다릅니다. 그래서 robots.txt를 파싱해 수집할 주소마다 can_fetch로 허용 여부를 판단했습니다.
코코재팬, 엔핍, 이로이로도쿄는 허용이었고, 재팬푸드몰은 오른쪽 아래처럼 사이트 전체가 금지여서 서비스에서 제외했습니다. 지금은 이 확인을 수집 전에 자동으로 하고, 허용되지 않으면 수집이 멈추게 했습니다.

## 8장 수집 종료 조건과 접근 차단 대응 (1분 30초)

### 이 장 이해하기
- **① 코코재팬 누락**: 페이지 수를 고정해 뒀는데 실제 페이지가 더 많았음 → "새 상품이 없으면 종료"로 변경. 수집이 끝까지 성공했을 때만 기존 CSV를 교체(`os.replace`)
- **② 이로이로도쿄 반복**: 마지막 페이지를 넘기면 오류(404) 대신 **메인 페이지로 리다이렉트**. 상태코드는 200이라 오류로 알 수 없었음 → 요청한 주소와 실제 도착한 주소(`res.url`)가 다르면 종료
- **③ GitHub Actions에서만 403**: User-Agent를 바꿔도 내 PC에서는 정상 → 응답 헤더를 기록해 보니 `cf-mitigated: challenge`(Cloudflare 봇 확인) → 우회하지 않고 코코재팬만 PC에서 수집한 데이터 사용
- 왼쪽 아래 코드: ①② 해결 코드 / 오른쪽 아래: ③ GitHub Actions 실행 기록

### 말할 대본
수집 중에 생긴 문제 세 가지와 원인을 좁힌 과정입니다.
첫째, 코코재팬 상품이 일부만 저장됐습니다. 오류 없이 끝나서 수집 범위를 의심했고, 시험 수집으로 세어 보니 실제 페이지가 제가 고정한 페이지 수보다 많았습니다. 그래서 새 상품이 없으면 끝나는 종료 조건으로 바꿨고, 실패해도 기존 데이터가 남도록 수집에 성공했을 때만 CSV를 교체하게 했습니다.
둘째, 이로이로도쿄에서는 같은 상품이 반복 수집됐습니다. 상태코드는 계속 200이었는데, 실제 도착한 주소를 보니 마지막 페이지 다음부터 메인 페이지로 리다이렉트되고 있었습니다. 그래서 요청한 주소와 도착한 주소가 다르면 수집을 끝내도록 했습니다.
셋째, GitHub Actions에서만 코코재팬이 403으로 막혔습니다. User-Agent를 바꿔도 제 PC에서는 모두 정상이라, 차단 응답의 헤더를 기록해 확인했더니 Cloudflare의 봇 확인이었습니다. 운영자가 둔 장치라 우회하지 않고, 코코재팬만 PC에서 수집한 데이터를 씁니다.

### 질문이 나오면
- **왜 GitHub 서버만 막혔나요?** 요청 내용이 아니라 요청이 나온 곳의 차이로 보고 있지만, 정확한 이유는 규명하지 못했습니다.

## 9장 데이터 정제와 분류 (50초)

### 이 장 이해하기
- **가격**: '1,900원'은 글자라서 정렬하면 '10,000원'이 '9,000원'보다 앞에 옴 → `re.sub(r'[^\d]', '', ...)`로 숫자가 아닌 글자를 지우고 정수로 변환
- **UNIQUE(site, url)**: 같은 쇼핑몰의 같은 상품 주소는 한 번만 저장하는 DB 규칙
- **분류**: 상품명에 '젤리'가 있으면 사탕·젤리처럼 키워드로 공통 분류 10개를 붙임
- **가장 뒤쪽 키워드 우선**: "초콜릿 커버 비스킷"에서 초콜릿(앞)과 비스킷(뒤)이 둘 다 나오면, 종류는 보통 끝에 오므로 비스킷 → 쿠키·디저트. 코드의 `rfind`가 뒤쪽 위치를 찾음

### 말할 대본
정제 단계의 문제는 모은 데이터를 그대로는 비교할 수 없다는 점이었습니다. 정제는 DB로 만들기 전에 형식을 맞추고, 누락과 중복을 걸러 내는 전처리입니다. 가격은 '1,900원' 같은 글자라서 그대로 정렬하면 '10,000원'이 '9,000원'보다 앞에 옵니다. 그래서 정규식으로 숫자만 남겨 정수로 바꿨습니다. 같은 상품이 반복 저장되는 것은 쇼핑몰과 상품 주소 조합에 UNIQUE 제약을 걸어 막았습니다.
분류는 사이트마다 없거나 기준이 달라서, 상품 이름의 키워드 규칙으로 공통 분류 10개를 붙였습니다. 상품 종류는 이름 끝에 오는 경우가 많아서, 여러 키워드가 함께 나오면 가장 뒤에 있는 키워드를 우선했습니다.

### 질문이 나오면
- **분류는 얼마나 정확한가요?** 처음에는 '기타'가 214개(약 11%)였는데, 결과를 직접 읽으며 규칙을 고쳐 25개(1% 안팎)로 줄였습니다.

## 10장 DB 설계와 구축 (1분)

### 이 장 이해하기
- 표는 `products` 표의 칸을 묶음별로, **저장할 때(build_db.py) 무엇을 하고, 조회할 때(app.py) 어디에 쓰는지** 보여 줍니다. 선생님이 말한 "가져올 땐 어떻게, 불러 쓸 땐 어떻게"에 대한 답입니다.
  - 식별(site, site_label, url): 저장 때 `UNIQUE(site, url)`로 중복 차단 → 조회 때 쇼핑몰 필터, 상품 페이지 이동
  - 가격(orig_price, sale_price, discount_pct): 저장 때 '1,900원' → 정수, 할인율 계산 → 조회 때 가격대·할인율 필터, 가격순 정렬
  - 분류(category, main_category): 원래 분류 보관 + 공통 10개 → 분류 필터
  - 검색용(name_norm, name_cho): 저장 때 공백 제거 이름과 초성을 **미리 계산** → 조회 때 이름·초성 검색
- 아래 코드: INSERT 문의 값은 물음표 12개로 따로 전달
- **구축**: 매주 수집 후 새 DB를 만들고, 상품이 3,000건 미만이면 수집이 끊긴 것으로 보고 실패 처리합니다(`weekly-crawl.yml`).

### 말할 대본
정제한 데이터는 products 표 하나로 설계했습니다. 표에서 보시는 것처럼 칸마다 저장할 때 할 일과 조회할 때 쓰임을 정해 두었습니다.
가격은 저장할 때 정수로 바꿔 두어서 조회할 때 바로 가격대 필터와 가격순 정렬에 쓰고, 같은 쇼핑몰의 같은 상품 주소는 UNIQUE 제약으로 한 번만 저장되게 했습니다. 검색은 공백을 지운 이름과 초성을 저장할 때 미리 계산해 두어서, 검색할 때마다 다시 계산하지 않게 했습니다.
DB는 읽기 위주의 작은 규모라 서버 설치가 필요 없는 SQLite를 골랐고, 매주 새로 만든 DB는 상품 수를 검증한 뒤에 씁니다.

### 질문이 나오면
- **표를 하나로 한 이유는?** 쇼핑몰 세 곳 모두 상품명·가격·이미지·링크라는 같은 정보만 있어서, 쇼핑몰 칸(site)으로 구분하면 한 표로 충분했습니다.
- **데이터가 많아지면요?** 동시에 쓰는 이용자가 많아지면 PostgreSQL 같은 서버형 DB로 옮겨야 합니다.
- **UNIQUE에 실제로 걸린 적이 있나요?** 코드에서 같은 주소를 먼저 걸러서 UNIQUE까지 가는 중복은 없습니다. 마지막 안전장치입니다.

## 11장 검색 서비스 구현 (1분 10초)

### 이 장 이해하기
- 위 흐름: ① 입력(검색어·필터) → ② 요청(JavaScript가 fetch로 `/api/search`) → ③ 조건 조립(Flask) → ④ 조회(SQLite) → ⑤ 응답·출력(JSON → 상품 카드)
- **백엔드(Flask, app.py)**에서 고려한 것
  - 조건마다 WHERE 절을 만들되 값은 `?`로 따로 전달 → SQL 주입 차단
  - 정렬은 `?`를 못 쓰는 자리라 허용 목록(`SORTS`)에서만 선택
  - DB를 읽기 전용(`mode=ro`)으로 열고, 범위를 넘는 페이지 번호는 마지막 페이지로 보정
  - 응답: 전체 건수, 페이지 수, 상품 40개
- **프론트(JavaScript, app.js)**에서 고려한 것
  - 페이지 전체가 아니라 목록 부분만 다시 그림
  - 입력할 때마다 요청하지 않고 250ms 기다린 뒤 요청(디바운스), 늦게 도착한 이전 응답은 버림
  - 모든 글자를 `textContent`로 출력해 외부 상품명 속 스크립트가 실행되지 않음
  - 검색 상태를 주소(URL)에 저장해서 새로고침하거나 링크를 공유해도 그대로

### 말할 대본
검색 서비스는 이런 흐름으로 동작합니다. 사용자가 검색어나 필터를 바꾸면 JavaScript가 페이지를 새로 열지 않고 fetch로 검색 API에 데이터만 요청합니다.
백엔드인 Flask는 받은 조건으로 WHERE 절을 만들되, 값은 물음표로 따로 넘겨 SQL 주입을 막았습니다. 정렬 기준은 물음표를 쓸 수 없는 자리라 정해 둔 목록에서만 고르게 했고, DB는 읽기 전용으로 엽니다. 결과는 전체 건수와 페이지 수, 상품 40개를 JSON으로 돌려줍니다.
프론트에서는 이 JSON으로 목록 부분만 다시 그리는데, 상품명은 외부에서 가져온 값이라 textContent로만 출력해 스크립트가 실행되지 않게 했습니다. 또 글자를 칠 때마다 요청하지 않도록 잠깐 기다렸다가 요청하고, 늦게 도착한 이전 결과는 버려서 화면이 꼬이지 않게 했습니다. 검색 상태는 주소에 저장해서 새로고침해도 유지됩니다.

### 질문이 나오면
- **왜 React 같은 프레임워크를 안 썼나요?** 화면이 검색 목록 하나라서, 빌드가 필요한 프레임워크 없이 JavaScript만으로 충분하다고 판단했습니다.
- **왜 Flask였나요?** 화면 페이지와 검색 API를 한 서버에서 간단히 함께 제공할 수 있고, API 구조를 직접 설계해 볼 수 있어서였습니다.

## 12장 프로젝트 회고 (50초)

### 말할 대본

첫째, robots.txt를 수집을 마친 뒤에 확인해서 재팬푸드몰을 서비스에서 빼야 했습니다. 접속이 되는 것만으로 수집할 수 있다고 판단한 것이 원인이라, 접속 확인 단계에 robots.txt 확인을 함께 넣었어야 했습니다.
둘째, 오류 없이 끝났는데 누락과 반복 수집이 있었습니다. 사이트의 끝을 고정 페이지 수로 가정했고 수집 결과를 검증하지 않았기 때문에, 응답으로 종료를 판단하는 조건과 수집 건수 검증을 처음부터 설계했어야 했습니다.
셋째, DB를 수집마다 새로 만들어 가격 변동 이력이 남지 않습니다. 가격 비교 서비스라면 수집 일자별 가격을 저장하는 구조가 필요합니다.
정리하면 저는 문제가 생겼을 때 추측하지 않고 원인을 좁혀 확인하고, 아는 지식을 근거로 방법을 고르는 방식으로 이 서비스를 만들었습니다.
