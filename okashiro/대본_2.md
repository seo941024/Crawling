## 4장 문제 정의와 목표 (40초)

**[말할 대본]**
일본 과자나 식료품을 살 때 사이트가 많고 가격도 서로 달랐습니다. 가장 싼 곳을 찾으려면 사이트마다 들어가서 같은 상품을 따로 검색해야 했고, 그게 너무 번거로웠습니다. 그래서 한곳에서 검색하고 가격순으로 비교해서 최저가를 바로 찾을 수 있는 서비스를 목표로 삼았습니다. 이 목표를 이루려면 여러 사이트에서 데이터를 모아야 하고, 그 데이터가 서로 비교 가능해야 하며, 빠르게 찾을 수 있어야 했는데, 이것이 이후 세 단계의 출발점입니다.

**[알아둘 개념]**
- 이 서비스는 최저가를 자동 추천하지 않습니다. 같은 상품인지 이름만으로 판별하면 틀릴 수 있어서, 이용자가 가격순으로 직접 비교하게 했습니다.

## 5장 서비스 시연 (80초, 영상)

**[말할 대본]**
완성된 서비스를 먼저 보여드리겠습니다.
(영상 중) 상품을 이름이나 초성으로 검색하고, 분류와 가격대, 할인율, 쇼핑몰로 좁힌 뒤, 가격순으로 정렬합니다. 마음에 드는 상품을 누르면 해당 쇼핑몰의 상품 페이지가 새 탭으로 열립니다. 새 탭으로 연 이유는 비교하던 목록 화면을 그대로 유지하기 위해서입니다.
이 화면은 서버가 상품 데이터를 JSON으로 주고, 브라우저의 JavaScript가 목록만 새로 그리는 구조입니다. 이렇게 나눈 이유는 필터나 정렬을 바꿀 때마다 페이지 전체를 다시 불러오지 않기 위해서입니다.

**[알아둘 개념] 서비스 구조** (식당 비유)
| 식당 | 서비스 | 역할 |
|---|---|---|
| 손님 | 브라우저(JavaScript) | 검색어 입력, 결과 표시 |
| 주방 | Flask 서버 | 요청을 받아 상품 조회 |
| 창고 | SQLite DB | 정리된 상품 보관 |

"ㄱㅇㅈㄹ" 검색 흐름: ① Flask가 화면 틀(HTML·CSS·JavaScript)을 보냄 → ② 입력하면 JavaScript가 fetch로 `/api/search?q=ㄱㅇㅈㄹ` 요청 → ③ Flask가 SQLite에서 조회(전부 자음이면 초성 칼럼) → ④ 결과를 JSON(총 개수·페이지 수·상품 40개)으로 응답 → ⑤ JavaScript가 상품 카드만 새로 그림 → ⑥ 카드 클릭 시 쇼핑몰 페이지가 새 탭으로 열림.
- Flask: 파이썬으로 웹 서버를 만드는 도구. 화면은 HTML·CSS·순수 JavaScript.
- `textContent`: 상품명을 글자로만 출력해서, 상품명에 스크립트가 섞여 있어도 실행되지 않게 함.

## 6장 파이프라인과 기술 스택 (60초)

**[말할 대본]**
전체를 세 단계로 나눈 이유는 단계마다 해결할 문제가 다르기 때문입니다. 수집 단계는 사이트마다 구조가 달라서 정적 사이트는 requests, 동적 사이트는 Selenium으로 나눴습니다. 검증·정제 단계는 가격이 문자열이고 분류 기준이 제각각이라서, 가격은 숫자로 바꾸고 분류는 원인을 설명할 수 있는 키워드 규칙으로 했습니다. 저장·서비스 단계는 SQLite와 Flask를 썼는데, SQLite는 서버 설치가 필요 없고 읽기 위주의 규모에 충분해서, Flask는 화면과 데이터 구조를 직접 설계할 수 있어서 선택했습니다. 수집은 GitHub Actions로 주 1회 자동 실행하게 해서 데이터를 최신으로 유지합니다.

**[알아둘 개념]**
- 파이프라인: 데이터가 단계를 거치며 흐르는 구조. 앞 단계의 결과가 다음 단계의 입력.
- requests: 파이썬으로 웹페이지를 받아 오는 도구. BeautifulSoup: 받은 HTML에서 원하는 태그를 뽑는 도구(`lxml`은 HTML을 해석하는 엔진). Selenium: 실제 브라우저를 코드로 조종하는 도구.
- 정규식: 문자열의 패턴을 찾는 규칙(여기서는 가격에서 숫자만 추출).
- SQLite: 파일 하나로 되는 DB. GitHub Actions: GitHub이 대신 코드를 실행해 주는 서비스(일정 지정 가능).

## 7장 수집 도구 선택 (70초)

**[말할 대본]**
수집에서 가장 먼저 한 일이 도구 선택입니다. 사이트가 상품을 보내는 방식이 두 가지라서 도구도 달라야 했기 때문입니다. 서버가 상품이 이미 들어 있는 HTML을 주는 정적 사이트는 requests로 받는 것으로 충분하고 가볍습니다. 반대로 자바스크립트가 상품을 나중에 만드는 동적 사이트는 requests로는 빈 틀만 받기 때문에, 브라우저를 실제로 실행하는 Selenium이 필요합니다. 어느 쪽인지는 같은 페이지를 두 방식으로 받아서 상품이 잡히는지 비교해서 판별했습니다.
표를 보면 사이트마다 페이지를 넘기는 방식도 달랐습니다. 주소의 번호로 넘기는 곳, 경로 번호로 넘기는 곳이 있었고, 코코재팬은 더보기 버튼이 내부 주소로 데이터를 받는 구조였습니다. 그래서 개발자도구로 그 주소를 찾아 직접 요청하는 방식으로 수집했습니다.

**[알아둘 개념]**
- 정적: 서버가 완성된 HTML을 보냄. 동적: 서버는 빈 틀, 브라우저에서 자바스크립트가 상품을 채움.
- 판별: 개발자도구(F12)에서는 보이는데 requests로 받은 HTML에는 없으면 동적.
- 페이지 이동 방식 3가지: URL 파라미터(`page=2`), 경로형(`/page/2/`), AJAX 더보기(내부 주소로 데이터 수신).
- **질문 대비**: 엔핍은 수집 당시 requests로 상품이 안 잡혀서 Selenium을 썼습니다. 이후 재확인에서는 requests로도 잡혔고, 사이트가 바뀐 것인지 당시 조건 차이인지는 규명하지 못했습니다.

## 8장 수집 허용 범위 확인 (60초)

**[말할 대본]**
수집하기 전에 허용 범위를 확인했습니다. 처음에는 접속이 되는지만 봤고, 상태코드 200이 나오니 수집할 수 있는 사이트라고 생각했습니다. 그런데 접속이 되는 것과 수집이 허용되는 것은 다릅니다. robots.txt는 운영자가 크롤러에게 접근 범위를 알려 주는 파일이라서, 이것이 허용 여부를 판단하는 기준이 됩니다. 그래서 파이썬의 can_fetch로 우리가 접근하는 주소가 허용되는지 확인했고, 재팬푸드몰이 사이트 전체 접근 거부로 되어 있었습니다. 운영자가 수집을 원하지 않는다는 의사 표시이므로, 이미 수집한 데이터였지만 서비스에서는 제외하고 원본은 로컬에만 보관합니다. 확인 시점이 수집을 마친 뒤였다는 점이 아쉬운 부분입니다.

**[알아둘 개념]**
- 상태코드: 200 정상, 403 접근 거부, 404 페이지 없음. 200은 "접속이 된다"일 뿐 "수집해도 된다"가 아님.
- robots.txt: `사이트주소/robots.txt`의 안내 파일. `User-agent: *`는 모든 크롤러, `Disallow: /`는 사이트 전체 접근 금지. 법적 강제력은 없지만 운영자의 의사 표시.
- can_fetch: 파이썬 `urllib.robotparser`의 함수. 주소의 허용 여부를 True/False로 알려 줌.
- 코코재팬·엔핍·이로이로도쿄는 허용, 재팬푸드몰만 전체 금지. 구루메상은 운영이 사실상 중단되어 제외.

## 9장 문제 해결 사례 (80초)

**[말할 대본]**
수집 중에 생긴 문제 세 가지를 원인을 찾은 과정과 함께 말씀드리겠습니다.
첫째, 코코재팬이 일부만 저장됐습니다. 코드는 정상 동작했기 때문에 수집 범위를 의심했고, 시험 수집으로 실제 페이지 수를 확인해 보니 제가 페이지 수를 고정해 둔 것이 원인이었습니다. 고정값은 사이트가 바뀌면 틀리기 때문에, 새 상품이 없으면 종료하는 조건으로 바꿨습니다.
둘째, 이로이로도쿄에서는 같은 상품이 반복 수집됐습니다. 보통 없는 페이지는 404가 오는데 상태코드로는 구분이 안 됐고, 응답의 최종 주소를 확인해 보니 마지막 페이지 뒤에 메인 페이지로 이동하고 있었습니다. 그래서 응답 주소와 요청 주소를 비교해서 종료하도록 했습니다.
셋째, GitHub Actions에서 코코재팬의 robots.txt만 403이 났습니다. 먼저 요청 내용이 원인인지 보려고 제 PC에서 User-Agent를 바꿔 시험했는데 모두 200이었습니다. 요청 내용이 아니라 요청이 나온 장소가 원인이라는 뜻이라서, 차단 응답의 헤더와 본문을 기록하게 해서 확인했고 Cloudflare의 봇 확인임을 알았습니다. 운영자가 자동화를 막으려는 장치이므로 우회하지 않고 코코재팬만 PC에서 수집합니다. GitHub 서버만 대상이 된 이유는 규명하지 못했습니다.

**[알아둘 개념]**
- 종료 조건: 마지막 페이지를 판단하는 규칙. 고정하지 않고 응답으로 판단(상품 없음, 새 상품 없음).
- 리다이렉트: 요청한 주소에서 다른 주소로 자동 이동시키는 것. 응답의 최종 주소(`res.url`)가 요청 주소와 다르면 이동당한 것.
- User-Agent: 요청에 붙는 접속 환경(브라우저 종류) 정보.
- Cloudflare 봇 확인: 웹사이트 앞단의 보안 서비스. 자동화로 의심되면 "Just a moment..." 확인 페이지를 보여 줌. 헤더 `cf-mitigated: challenge`가 그 표시.

## 10장 정제와 분류 (50초)

**[말할 대본]**
수집한 데이터는 그대로는 비교와 필터가 안 돼서 정제했습니다. 가격은 '1,900원' 같은 문자열이라 정렬하면 순서가 틀리기 때문에 정규식으로 숫자로 바꿨습니다. 같은 상품이 반복 저장되는 것은 DB 제약으로 막았습니다. 분류는 사이트마다 없거나 기준이 달라서 필터를 쓸 수 없었기 때문에, 상품 이름의 키워드로 공통 분류 10개를 직접 붙였습니다. 머신러닝은 정답 라벨이 없어서 쓰기 어렵고 틀렸을 때 원인을 설명하기도 어려워서, 원인을 설명할 수 있는 규칙 방식을 선택했습니다. 상품 종류는 이름 끝에 오는 경우가 많아서 가장 뒤에 나온 키워드를 우선합니다.

**[알아둘 개념]**
- 문자열 정렬 문제: `'10,000'`이 `'9,000'`보다 앞에 정렬됨(`'1'` < `'9'`). 숫자여야 정렬·가격대 필터가 맞음.
- 정규식 `[^\d]`: 숫자가 아닌 글자를 지우면 숫자만 남음.
- UNIQUE(site, url): 같은 쇼핑몰의 같은 상품 주소는 한 번만 저장.
- 분류: 이름에서 키워드를 찾음. "초콜릿 커버 비스킷"은 뒤에 나온 '비스킷' 기준으로 쿠키·디저트.
- 원본 분류는 이로이로도쿄에만 있고 엔핍·코코재팬은 없었음. 원본을 변환한 것이 아니라 이름 키워드로 새로 부여했고, 키워드가 없을 때만 원본 분류를 참고.
- 같은 상품을 이름 유사도로 자동으로 묶는 것은 표기 차이로 잘못 묶일 위험이 있어 하지 않음.

## 11장 저장과 조회 쿼리 (55초)

**[말할 대본]**
저장소로 SQLite를 선택했습니다. 이 서비스는 데이터를 읽는 일이 대부분이고 규모가 크지 않아서, 서버 설치가 필요 없는 SQLite로 충분하다고 판단했습니다. 조회 쿼리에서는 검색어를 SQL 문장에 이어 붙이지 않고 물음표로 따로 전달합니다. 그렇게 하지 않으면 검색어에 SQL을 섞어서 DB를 조작하는 SQL 주입이 가능하기 때문입니다. 초성 검색은 검색할 때마다 계산하면 비효율적이라서, 저장할 때 한 번만 계산해 칼럼에 넣어 두었습니다. 정렬 기준은 물음표를 쓸 수 없는 부분이라서, 정해 둔 허용 목록에서만 고르게 했습니다.

**[알아둘 개념]**
- 쿼리: DB에 보내는 명령. 저장은 INSERT, 조회는 SELECT.
- SELECT 예: `SELECT name, sale_price FROM products WHERE name_cho LIKE ? AND site IN (?, ?) AND sale_price <= ? ORDER BY discount_pct DESC LIMIT 40 OFFSET 0` (WHERE 조건, ORDER BY 정렬, LIMIT·OFFSET 페이지 처리).
- SQL 주입: 검색어에 `'; DROP TABLE ...` 같은 문장을 넣어 DB를 망가뜨리는 공격. `?`로 전달하면 값은 항상 글자로만 취급됨.
- ORDER BY에 ?를 못 쓰는 이유: 정렬 기준은 값이 아니라 SQL 문장의 일부.
- 초성 칼럼: 한글 글자는 `(글자코드 − 0xAC00) ÷ 588`로 초성 번호를 구할 수 있음(588 = 21×28).
- 읽기 전용 연결(`mode=ro`): 웹 요청이 DB를 실수로 바꾸지 못함.

## 예상 질문과 답 (이유 중심)

**Q. 왜 정적·동적을 구분했나요?**
정적 사이트에 Selenium을 쓰면 브라우저를 띄우느라 느리고 무겁고, 동적 사이트에 requests를 쓰면 빈 틀만 받기 때문입니다. 사이트마다 확인해서 맞는 도구를 썼습니다.

**Q. 엔핍이 동적이라고 했는데 지금은 requests로도 되던데요?**
수집 당시에는 requests로 상품이 잡히지 않아서 Selenium을 썼고, 이후 재확인에서는 두 방식 모두 잡혔습니다. 사이트가 바뀐 것인지 당시 조건이 달랐던 것인지는 규명하지 못했습니다. 그래서 판별 방법을 "같은 페이지를 두 방식으로 받아 비교"로 정리했습니다.

**Q. robots.txt는 법적으로 지켜야 하나요?**
법적 강제력은 없습니다. 하지만 운영자의 의사 표시이므로 존중하는 것을 기본으로 했습니다.

**Q. Cloudflare 봇 확인을 왜 우회하지 않았나요?**
운영자가 자동화 접근을 막으려는 장치이므로 우회하지 않는 것이 맞다고 판단했습니다.

**Q. 왜 머신러닝을 쓰지 않았나요?**
정답 라벨이 없고, 틀렸을 때 원인 설명이 어렵습니다. 키워드 규칙은 틀리면 규칙만 고치면 됩니다. 대신 새 상품명에는 규칙을 추가해야 합니다.

**Q. 같은 상품인데 이름이 다르면요?**
이름 유사도로 자동으로 묶으면 다른 상품이 묶일 수 있어서 하지 않았고, 이용자가 가격순으로 직접 비교하게 했습니다.

**Q. SQL 주입을 어떻게 막았나요?**
값을 SQL 문장에 이어 붙이지 않고 물음표로 따로 전달합니다. 물음표를 쓸 수 없는 정렬 기준은 허용 목록에서만 고르게 했습니다.

**Q. 왜 SQLite인가요? 규모가 커지면요?**
서버 설치가 필요 없고 읽기 위주라 충분했습니다. 이용자가 늘면 PostgreSQL 같은 서버형 DB로 옮겨야 합니다.

**Q. 데이터를 최신으로 유지하는 방법은요?**
GitHub Actions로 주 1회 일요일 새벽에 자동 수집합니다. 별도 서버가 필요 없습니다. 코코재팬만 PC에서 수집합니다.

**Q. 공개해도 되나요?**
이용약관에 정보 복제·제공 제한이 있어서 공개 배포는 사전 허락이 필요하다고 보고 현재는 로컬에서 시연합니다.

**Q. 가장 어려웠던 점은?**
