## 2장 1. 프로젝트 개요 (1분)

### 이 장 이해하기
- 문제는 "상황"이 아니라 "겪는 불편"입니다. 첫 줄(개별 검색·수동 비교)은 수집·서비스로, 둘째 줄(기준이 다름)은 정제로 이어집니다.
- 기술 스택은 코드에서 직접 쓴 것, 활용 도구는 개발할 때 쓴 것입니다.

### 말할 대본
일본 과자를 대행 구매할 때, 가장 싼 곳을 찾으려면 사이트마다 들어가 검색하고 가격을 직접 비교해야 했습니다. 게다가 사이트마다 표기와 분류 기준이 달라 같은 상품끼리 비교하기도 어려웠습니다.
그래서 여러 쇼핑몰 상품을 한곳에서 검색하고 가격순으로 비교하는 서비스를 목표로 했습니다. 이 프로젝트로 보여드리고 싶은 역량은 사이트 구조 분석, 데이터 검증·정제, 조회 쿼리 설계입니다.
수집에 requests, BeautifulSoup, Selenium, 저장에 SQLite, 서비스에 Flask와 JavaScript를 썼고, 예약 수집은 GitHub Actions, 개발 보조로 Claude Code를 활용했습니다.

### 질문이 나오면
- **Claude Code는 어떻게?** 코드 작성과 오류 원인 점검에 보조로 썼고, 어떤 방법을 쓸지 설계하고 결과가 맞는지 검증하는 건 직접 했습니다.

## 3장 2. 서비스 화면 (1분, 영상)

### 이 장 이해하기
- 오른쪽 시연 흐름: 상품 검색(이름·초성) → 조건 필터 → 가격순 정렬 → 쇼핑몰 이동
- 구성: Flask가 JSON으로 데이터만 주고, JavaScript가 fetch로 받아 목록만 갱신. 글자는 textContent로 출력(스크립트 실행 차단)

### 말할 대본

화면은 Flask가 상품 데이터만 JSON으로 보내고, JavaScript가 목록 부분만 다시 그리는 구조입니다.

## 5장 4. 데이터 수집 과정 (1분 10초)

### 이 장 이해하기
- 표: 사이트별 유형, 사용 기술, 페이지 이동 방식. 재팬푸드몰(robots.txt 금지)과 구루메상(운영 중단)은 수집했지만 서비스에서 제외
- F12 캡처: 상품 카드 하나(`li.sct_li`)를 찾고, 그 안에서 상품명(`sct_txt`), 정가(`coco2-was`), 할인가(`coco2-now`)를 꺼냄
- 오른쪽 위 상자: 정적 수집 실패 → 동적 수집으로 전환 (엔핍)
- 오른쪽 아래 상자: 페이지 이동과 종료 판단 (페이지 번호·'더보기' 주소를 바꿔 가며 요청, 새 상품이 없거나 리다이렉트되면 종료)

### 말할 대본
사이트마다 상품을 보내는 방식이 달랐습니다. 엔핍은 requests로 받은 HTML에 상품 정보가 없었는데 브라우저 화면에는 상품이 있어서, JavaScript가 상품을 나중에 채우는 동적 페이지로 판단하고 Selenium으로 수집했습니다. 나머지는 requests로 받은 HTML에 상품이 있어서 가볍고 빠른 requests를 썼습니다.
상품은 개발자도구로 상품 카드 하나의 태그와 클래스를 분석해서 카드 단위로 찾고, 그 안에서 상품명과 가격을 꺼냈습니다. 페이지는 번호나 코코재팬 '더보기' 버튼의 내부 주소를 바꿔 가며 요청했고, 새 상품이 더 나오지 않거나 다른 주소로 보내지면 마지막 페이지로 판단해 멈췄습니다.

### 질문이 나오면
- **3초는 왜?** 상품이 채워지는 시간을 보고 여유 있게 잡았습니다. 더 정확하게는 상품 요소가 나타날 때까지 기다리는 WebDriverWait를 쓸 수 있습니다.
- **요청 간격은?** 짧은 간격으로 몰아서 요청하면 접속이 차단될 수 있어, 수집이 끝까지 안정적으로 진행되도록 2~4초씩 기다렸습니다.

## 6장 5. 데이터 정제와 분류 (50초)

### 이 장 이해하기
- 정제: DB에 넣기 전에 형식을 맞추고 누락·중복을 거르는 전처리
- '1,900원'은 글자라 '10,000원'이 '9,000원'보다 앞에 정렬됨 → 숫자만 남겨 정수로
- 가장 뒤쪽 키워드 우선: "초콜릿 커버 비스킷"은 뒤의 비스킷 → 쿠키·디저트

### 말할 대본
모은 데이터는 그대로는 비교할 수 없었습니다. 가격은 '1,900원' 같은 글자라 정렬이 틀려서 정규식으로 숫자만 남겨 정수로 바꿨고, 같은 상품의 반복 저장은 UNIQUE 제약으로 막았습니다. 분류는 사이트마다 없거나 기준이 달라 상품명 키워드로 공통 분류 10개를 붙였고, 상품 종류는 이름 끝에 오는 경우가 많아 가장 뒤쪽 키워드를 우선했습니다.

### 질문이 나오면
- **분류 정확도?** 처음 '기타'가 214개(약 11%)였는데 결과를 직접 읽으며 규칙을 고쳐 25개로 줄였습니다.

## 7장 6. DB 설계와 구축 (1분)

### 이 장 이해하기
- products 표 하나. 칸마다 저장할 때 할 일과 조회할 때 쓰임
- 검색용 칸(name_norm, name_cho)은 저장할 때 미리 계산 → 검색할 때 다시 계산하지 않음

### 말할 대본
정제한 데이터는 products 표 하나로 설계했습니다. 가격은 저장할 때 정수로 바꿔 두어 조회할 때 바로 가격대 필터와 정렬에 쓰고, 같은 쇼핑몰의 같은 상품 주소는 UNIQUE로 한 번만 저장됩니다. 검색용으로 공백을 지운 이름과 초성을 미리 계산해 두었습니다.
DB는 읽기 위주의 작은 규모라 SQLite를 골랐고, 매주 새로 만든 DB는 상품 수를 검증한 뒤에 씁니다.

### 질문이 나오면
- **이미지를 DB에 안 넣은 이유?** DB가 커지고 느려져서, 이미지 파일은 PC 폴더(static/images)에 두고 DB에는 경로만 저장했습니다.
- **데이터가 많아지면?** 동시 사용자가 많아지면 PostgreSQL 같은 서버형 DB로 옮겨야 합니다.

## 8장 7. 검색 서비스 구현 (1분 10초)

### 이 장 이해하기
- 흐름: 입력 → fetch 요청 → Flask가 조건 조립 → SQLite 조회 → JSON → 상품 카드
- 백엔드: 값은 `?` 파라미터(SQL 주입 차단), 정렬은 허용 목록, 읽기 전용 DB
- 프론트: 250ms 대기 후 요청(디바운스), 늦게 온 응답 버림, textContent 출력, 검색 상태를 주소에 저장

### 말할 대본
사용자가 검색어나 필터를 바꾸면 JavaScript가 페이지를 새로 열지 않고 검색 API에 데이터만 요청합니다. Flask는 조건으로 WHERE 절을 만들되 값은 물음표로 따로 넘겨 SQL 주입을 막고, 정렬은 정해 둔 목록에서만 고르며, DB는 읽기 전용으로 엽니다.
화면에서는 받은 JSON으로 목록만 다시 그리고, 상품명은 textContent로만 출력해 스크립트가 실행되지 않게 했습니다. 입력할 때마다 요청하지 않도록 잠깐 기다렸다가 요청하고, 검색 상태는 주소에 저장해 새로고침해도 유지됩니다.

### 질문이 나오면
- **왜 React 안 썼나?** 화면이 검색 목록 하나라 빌드가 필요한 프레임워크 없이 JavaScript만으로 충분했습니다.

## 9장 8. 프로젝트 수행 경험 (1분 40초)

### 이 장 이해하기
- 위 표 **01 시행착오와 개선**: 문제 → 원인 확인 → 해결 4가지 (기존 수집 허용·수집 문제 두 장을 합친 것)
  - 재팬푸드몰: 처음엔 접속(200)만 확인 → robots.txt가 전체 금지 → 서비스 제외, 수집 전 자동 확인
  - 코코재팬 누락: 고정 페이지 수 < 실제 페이지 수 → 새 상품 없으면 종료, 성공 시에만 CSV 교체
  - 이로이로도쿄 반복: 마지막 페이지 이후 메인으로 리다이렉트(200) → 요청·도착 주소 비교
  - GitHub 403: 응답 헤더 cf-mitigated: challenge(Cloudflare 봇 확인) → 우회 없이 PC 수집
- 아래 표 **02 아쉬운 점과 개선 필요 사항**: "앞으로 할 계획"이 아니라 "부족했던 것"
- 세부 근거(코드, robots.txt 화면, GitHub 로그)는 Reference 1·2

### 말할 대본
수행하면서 겪은 문제와 해결입니다.
처음에는 접속이 되는지만 보고 수집했는데, robots.txt를 확인해 보니 재팬푸드몰은 사이트 전체가 금지여서 서비스에서 빼고, 지금은 수집 전에 자동으로 확인합니다.
코코재팬은 고정해 둔 페이지 수가 실제보다 적어 일부가 빠져서 새 상품이 없으면 끝나는 조건으로 바꿨고, 이로이로도쿄는 마지막 페이지 다음이 메인 페이지로 보내져 같은 상품이 반복돼서 요청한 주소와 도착한 주소를 비교해 멈췄습니다. GitHub Actions에서만 난 코코재팬 403은 응답 헤더로 Cloudflare 봇 확인임을 찾았고, 우회하지 않고 PC에서 수집합니다.
아쉬운 점은 세 가지입니다. robots.txt 확인을 접속 확인 단계에 함께 넣었어야 했고, 응답 기반 종료 조건과 수집 건수 검증을 처음부터 설계했어야 했으며, 가격 변동 이력을 남기는 구조가 필요합니다.
정리하면 저는 문제가 생겼을 때 추측하지 않고 원인을 좁혀 확인하고, 아는 지식을 근거로 방법을 골라 이 서비스를 만들었습니다.

### 질문이 나오면
- **왜 GitHub 서버만 403?** 요청이 나온 곳의 차이로 보고 있지만, Cloudflare 내부 판단이라 정확한 이유는 확인하지 못했습니다. 처음 실행부터 403이었고, 제 PC에서는 계속 200이었습니다.
- **코드를 보여 줄 수 있나?** Reference 1·2에 robots.txt 확인 코드와 종료 조건 코드, GitHub 로그가 있습니다.
