## 5장 서비스 시연 (80초, 영상 재생)

**[말할 대본]**
먼저 완성된 서비스를 영상으로 보여드리겠습니다.
(영상 재생 중 설명) 상품을 이름이나 초성으로 검색하고, 분류와 가격대, 할인율, 쇼핑몰로 필터링한 뒤, 가격순으로 정렬해서 비교합니다. 마음에 드는 상품을 누르면 해당 쇼핑몰의 상품 페이지로 이동합니다.

**[알아둘 개념] 서비스 구조 (가장 중요한 부분)**
비유: **식당**입니다.

| 식당 | 서비스 | 하는 일 |
|---|---|---|
| 손님 | 브라우저(화면, JavaScript) | 검색어를 입력하고 결과를 봄 |
| 주방 | Flask 서버(app.py) | 요청을 받아 상품을 찾아 줌 |
| 창고 | SQLite DB(okashieri.db) | 정리된 상품을 보관 |

"ㄱㅇㅈㄹ"을 검색하면 일어나는 일입니다.
1. 사이트에 들어오면 Flask가 **화면 틀**(HTML, CSS, JavaScript)을 보냅니다. 처음에는 상품이 비어 있습니다.
2. 검색창에 입력하면 JavaScript가 **fetch**로 서버에 요청합니다. 주소는 `/api/search?q=ㄱㅇㅈㄹ` 형태입니다.
3. Flask가 요청을 받아 **SQLite에서 조회**합니다. 검색어가 전부 자음이면 초성 칼럼에서 찾습니다.
4. 결과를 **JSON**으로 돌려줍니다. JSON은 데이터를 주고받는 글자 형식으로, 총 몇 개인지, 몇 페이지인지, 상품 40개의 이름·가격·할인율·주소가 들어 있습니다.
5. JavaScript가 받은 데이터로 **상품 카드만 새로 그립니다.** 페이지 전체를 새로고침하지 않아서 필터와 정렬을 바꿔도 빠릅니다.
6. 카드를 누르면 쇼핑몰 상품 페이지가 **새 탭**으로 열립니다. 비교하던 목록은 그대로 남습니다.

- Flask: 파이썬으로 웹 서버를 만드는 도구입니다. 화면은 Flask가 아니라 HTML·CSS·순수 JavaScript로 만들었습니다(React 같은 프레임워크는 쓰지 않음).
- 안전하게 만든 부분: 값을 `?`로 따로 전달(SQL 주입 방지), `textContent`로 글자만 출력(상품명 속 스크립트 실행 방지), DB를 읽기 전용으로 연결.

## 6장 데이터 파이프라인과 기술 스택 (60초)

**[말할 대본]**
전체는 수집, 검증·정제, 저장·서비스의 세 단계입니다. 수집은 정적 사이트는 requests, 동적 사이트는 Selenium으로 나눴습니다. 검증·정제에서는 가격을 숫자로 바꾸고 분류는 키워드 규칙으로 했습니다. 저장은 서버 설치가 필요 없는 SQLite를 썼고, 서비스는 구조를 직접 설계할 수 있는 Flask를 썼습니다. 수집은 GitHub Actions로 주 1회 자동으로 실행합니다. 이제 단계별로 어떤 판단을 했는지 설명드리겠습니다.

**[알아둘 개념] 도구 하나씩**
- **파이프라인**: 데이터가 단계를 거쳐 흐르는 구조입니다. 앞 단계의 결과가 다음 단계의 입력이 됩니다.
- **requests**: 파이썬으로 웹페이지를 요청해서 받아 오는 도구입니다. 브라우저 없이 HTML만 받습니다.
- **BeautifulSoup**: 받은 HTML에서 "이 클래스의 태그를 찾아라"처럼 원하는 부분을 뽑는 도구입니다. 파서 `lxml`은 BeautifulSoup 안에서 HTML을 해석하는 엔진입니다.
- **Selenium**: 실제 크롬 브라우저를 코드로 조종하는 도구입니다. 자바스크립트가 실행된 뒤의 화면을 얻을 수 있습니다.
- **정규식**: 문자열에서 패턴을 찾는 규칙입니다. 여기서는 가격 문자열에서 숫자만 뽑는 데 썼습니다.
- **SQLite**: 파일 하나로 되는 DB입니다. 서버 설치가 필요 없습니다.
- **GitHub Actions**: GitHub이 대신 코드를 실행해 주는 서비스입니다. 일정에 맞춰 자동 실행도 됩니다.
- 발표 중 단계 이름(수집 → 검증·정제 → 저장·서비스)을 먼저 짚고 가면 이후 장이 같은 순서로 이어져서 듣기 쉽습니다.

## 7장 수집 도구 선택 (70초)

**[말할 대본]**
수집에서 먼저 한 판단은 도구 선택입니다. 사이트가 상품을 보내는 방식이 두 가지입니다. 서버가 상품이 이미 들어 있는 HTML을 주는 정적 사이트는 requests로 가볍게 받고, 자바스크립트가 상품을 나중에 만드는 동적 사이트는 브라우저가 실제로 실행돼야 해서 Selenium을 썼습니다. 어느 쪽인지는 같은 페이지를 두 방식으로 받아 보고 결과를 비교해서 판별했습니다. 표를 보면 코코재팬, 이로이로도쿄는 정적이라 requests, 엔핍은 동적이라 Selenium을 썼고, 페이지를 넘기는 방식도 사이트마다 달라서 각각 분석했습니다. 코코재팬의 더보기 버튼은 내부 주소로 데이터를 받는 구조라서, 그 주소를 직접 요청했습니다.

**[알아둘 개념]**
- **정적 사이트**: 서버가 완성된 HTML을 한 번에 보냅니다. 받자마자 상품이 들어 있습니다.
- **동적 사이트**: 서버는 빈 틀을 보내고, 브라우저에서 자바스크립트가 실행되며 상품을 채웁니다. requests로 받으면 상품이 없는 빈 틀만 옵니다.
- **판별 방법**: 개발자도구(F12)에서는 보이는데 requests로 받은 HTML에는 없으면 동적입니다.
- **페이지 이동 방식 세 가지**
  - URL 파라미터: `...page=2` (엔핍, 구루메상)
  - 경로형: `.../page/2/` (이로이로도쿄)
  - AJAX 더보기: 주소는 그대로고 버튼을 누르면 내부 주소로 데이터를 받음 (코코재팬). 개발자도구 Network 탭에서 그 주소를 찾아 직접 요청했습니다.
- **주의(질문 대비)**: 엔핍은 **수집할 때** requests로 받으면 상품이 잡히지 않아서 Selenium을 썼습니다. 그런데 최근에 다시 시험하니 requests로도 상품이 잡혔습니다. 사이트가 바뀌었는지, 당시 조건이 달랐는지는 규명하지 못했습니다. 질문이 오면 이렇게 사실대로 말하세요. "수집 당시에는 requests로 안 잡혀서 Selenium을 썼고, 지금은 사이트가 바뀌어서 두 방식 모두 되는 것을 확인했습니다. 어느 쪽인지 판별하는 방법은 같은 페이지를 두 방식으로 받아 보는 것입니다."

## 8장 수집 허용 범위 확인 (60초)

**[말할 대본]**
수집 전에 허용 범위를 확인했습니다. 처음에는 접속이 되는지만 확인했습니다. 상태코드 200이 나오니 수집할 수 있는 사이트라고 생각했습니다. 그런데 접속이 된다고 수집이 허용되는 것은 아니었습니다. robots.txt는 사이트 운영자가 크롤러의 접근 범위를 알려 주는 파일이라서, 파이썬의 can_fetch로 우리가 접근하는 주소가 허용되는지 확인했습니다. 그 결과 재팬푸드몰이 사이트 전체 접근 거부로 되어 있었습니다. 그래서 이미 수집한 데이터지만 서비스에서는 제외하고, 원본은 로컬에만 보관하고 있습니다. 확인 시점이 수집을 마친 뒤였다는 점이 아쉬운 부분입니다.

**[알아둘 개념]**
- **상태코드**: 요청 결과를 나타내는 숫자입니다. 200은 정상, 403은 접근 거부, 404는 페이지 없음입니다. 200은 "접속이 된다"일 뿐 "수집해도 된다"는 뜻이 아닙니다.
- **robots.txt**: `사이트주소/robots.txt`에 있는 안내 파일입니다. `User-agent: *`는 모든 크롤러에게 하는 말이고, `Disallow: /`는 사이트 전체 접근 금지를 뜻합니다. 법적 강제력은 없는 관례지만 운영자의 의사 표시입니다.
- **can_fetch**: 파이썬 기본 모듈 `urllib.robotparser`의 함수로, 특정 주소의 접근 허용 여부를 True/False로 알려 줍니다.
- 코코재팬·엔핍·이로이로도쿄는 우리가 접근한 주소가 허용됐고, 재팬푸드몰만 전체 금지였습니다. 구루메상은 robots.txt와 별개로 운영이 사실상 중단된 사이트(더미 상품 다수)라 제외했습니다.

## 9장 문제 해결 사례 (80초)

**[말할 대본]**
수집하면서 생긴 문제 세 가지를 말씀드리겠습니다.
첫째, 코코재팬 수집 결과가 일부만 저장됐습니다. 시험 수집으로 실제 페이지 수를 확인해 보니, 페이지 수를 고정해 둔 것이 원인이었습니다. 그래서 새 상품이 없으면 종료하는 조건으로 바꿨습니다.
둘째, 이로이로도쿄에서는 같은 상품이 계속 반복 수집됐습니다. 마지막 페이지 뒤의 응답 주소를 확인했더니, 404가 아니라 메인 페이지로 이동하고 있었습니다. 그래서 응답 주소와 요청 주소를 비교해서 종료를 판단했습니다.
셋째, GitHub Actions에서 코코재팬의 robots.txt만 403이 났습니다. 제 PC에서는 User-Agent를 바꿔도 모두 200이었고, GitHub에서 차단 응답의 헤더와 본문을 기록하게 해서 확인했더니 Cloudflare의 봇 확인이었습니다. 이를 우회하지 않고 코코재팬만 PC에서 수집합니다. GitHub 서버만 대상이 된 이유는 규명하지 못했습니다.

**[알아둘 개념]**
- **종료 조건**: 마지막 페이지를 판단하는 규칙입니다. "페이지 수는 8"처럼 고정하면 사이트가 바뀔 때 틀립니다. 그래서 "상품이 없거나 새 상품이 없으면 종료"로 정했습니다(응답 기준).
- **리다이렉트**: 요청한 주소에서 다른 주소로 자동으로 이동시키는 것입니다. 보통은 없는 페이지에 404가 오는데, 이로이로도쿄는 메인으로 이동시켜서 상태코드로는 구분이 안 됐습니다. 응답의 최종 주소(`res.url`)가 요청한 주소와 다른지 비교하면 알 수 있습니다.
- **User-Agent**: 요청에 붙는 접속 환경 정보(브라우저 종류)입니다. 값을 바꿔도 PC에서 모두 200이었으니, 요청 내용이 아니라 요청이 나온 장소가 원인이라는 판단의 근거였습니다.
- **Cloudflare 봇 확인(챌린지)**: Cloudflare는 웹사이트 앞에서 트래픽을 걸러 주는 서비스입니다. 자동화된 요청으로 의심되면 "Just a moment..." 확인 페이지를 보여 줍니다. 응답 헤더 `cf-mitigated: challenge`가 그 표시입니다. 이 확인 페이지를 자동으로 통과시키는 방법도 있지만, 운영자의 차단 의사를 존중해서 우회하지 않았습니다.
- **규명하지 못했다**: "GitHub 서버만 대상이 된 이유"는 Cloudflare 내부 판단이라 밖에서 확인할 수 없었습니다.

## 10장 정제와 분류 (50초)

**[말할 대본]**
수집한 데이터는 그대로는 비교하거나 필터할 수 없어서 정제했습니다. 가격은 '1,900원' 같은 문자열이라서 정규식으로 숫자로 바꿨고, 같은 상품이 반복 저장되는 것은 DB 제약으로 막았습니다. 분류는 사이트마다 없거나 기준이 달라서, 상품 이름의 키워드 규칙으로 공통 분류 10개를 만들었습니다. 머신러닝은 정답 라벨이 없어서 쓰기 어려웠고, 규칙 방식은 잘못 분류됐을 때 원인을 설명할 수 있습니다. 상품 종류는 이름 끝에 오는 경우가 많아서, 가장 뒤에 나온 키워드를 우선합니다.

**[알아둘 개념]**
- **문자열 가격의 문제**: `'10,000'`과 `'9,000'`을 문자열로 정렬하면 `'1'`이 `'9'`보다 작아서 순서가 틀립니다. 숫자여야 정렬·가격대 필터가 맞습니다.
- **정규식**: 문자열의 패턴을 찾는 규칙입니다. `[^\d]`는 "숫자가 아닌 글자"를 뜻해서, 지우면 숫자만 남습니다.
- **UNIQUE(site, url)**: "같은 쇼핑몰의 같은 상품 주소는 한 번만 저장"이라는 DB 규칙입니다.
- **분류 방식**: 이름에서 키워드를 찾아 분류합니다. 예: "초콜릿 커버 비스킷"은 '초콜릿'과 '비스킷'이 모두 있지만 뒤에 나온 '비스킷' 기준으로 쿠키·디저트로 갑니다.
- **원본 분류**: 이로이로도쿄에만 있고, 엔핍과 코코재팬은 아예 분류가 없었습니다. 그래서 원본 분류를 변환하는 방식이 아니라 이름 키워드로 분류를 새로 붙였습니다. 이름에서 키워드를 찾지 못할 때만 원본 분류를 참고합니다.
- **머신러닝을 안 쓴 이유**: 학습에 필요한 정답 라벨(상품마다 올바른 분류)이 없고, 틀렸을 때 원인을 설명하기 어렵습니다.
- 같은 상품을 이름 유사도로 자동으로 묶는 방법은 표기 차이로 잘못 묶일 위험이 있어서 하지 않았습니다. 이용자가 가격순으로 직접 비교하게 했습니다.

## 11장 저장과 조회 쿼리 (55초)

**[말할 대본]**
저장은 SQLite를 썼습니다. 서버 설치가 필요 없고, 읽기 위주의 규모에서는 충분하다고 판단했습니다. 조회는 값을 물음표로 따로 전달하는 쿼리로 했습니다. 이렇게 하면 검색어에 SQL이 섞여 있어도 실행되지 않아서 SQL 주입을 막을 수 있습니다. 초성 검색은 저장할 때 초성을 한 번 계산해서 칼럼에 넣어 두었고, 정렬은 물음표를 쓸 수 없는 부분이라서 정해 둔 허용 목록에서만 고르게 했습니다.

**[알아둘 개념]**
- **쿼리**: DB에 보내는 명령입니다. 저장은 `INSERT`, 조회는 `SELECT`입니다.
- **SELECT 예**: `SELECT name, sale_price FROM products WHERE name_cho LIKE ? AND site IN (?, ?) AND sale_price <= ? ORDER BY discount_pct DESC LIMIT 40 OFFSET 0`
  - `WHERE`: 조건, `ORDER BY`: 정렬, `LIMIT 40 OFFSET 0`: 0번째부터 40개씩(페이지 처리).
- **? 파라미터와 SQL 주입**: 검색어를 SQL 문장에 이어 붙이면, 누군가 `'; DROP TABLE...` 같은 문장을 넣어 DB를 망가뜨릴 수 있습니다. `?`로 값을 따로 전달하면 그 값은 항상 글자로만 취급됩니다.
- **ORDER BY에 ?를 못 쓰는 이유**: 정렬 기준은 값이 아니라 SQL 문장의 일부라서 `?`로 바꿀 수 없습니다. 그래서 `discount`, `price_asc` 같은 정해 둔 값(허용 목록)에서만 고르게 했습니다.
- **초성 칼럼**: 한글 글자는 유니코드에서 초성·중성·종성의 조합이라서, `(글자코드 − 0xAC00) ÷ 588`로 초성 번호를 구할 수 있습니다(588 = 21×28). 저장할 때 한 번만 계산하면 검색 때마다 계산하지 않아도 됩니다.
- **읽기 전용 연결**: DB를 `mode=ro`로 열어서, 웹 요청이 실수로 데이터를 바꾸지 못합니다.

## 예상 질문과 답

**Q. 왜 정적과 동적을 구분했나요?**
정적 사이트에 Selenium을 쓰면 브라우저를 띄우느라 느리고 무겁고, 동적 사이트에 requests를 쓰면 상품이 없는 빈 HTML만 받기 때문입니다. 그래서 사이트별로 확인해서 맞는 도구를 썼습니다.

**Q. 엔핍이 동적이라고 했는데 지금은 requests로도 되던데요?**
수집할 당시에는 requests로 받으면 상품이 잡히지 않아서 Selenium을 썼습니다. 이후에 다시 확인했을 때는 두 방식 모두 상품이 잡혔고, 사이트가 바뀐 것인지 당시 조건이 달랐던 것인지는 규명하지 못했습니다. 그래서 판별 방법 자체를, 같은 페이지를 두 방식으로 받아 비교하는 것으로 정리했습니다.

**Q. robots.txt는 법적으로 지켜야 하나요?**
법적 강제력이 있는 규칙은 아닙니다. 하지만 운영자의 의사 표시라서 존중하는 것을 기본으로 했습니다. 재팬푸드몰은 전체 접근 거부여서 서비스에서 제외했습니다.

**Q. Cloudflare 봇 확인을 우회하지 않은 이유는?**
운영자가 자동화된 접근을 막으려고 설정한 것이라서, 우회하지 않는 것이 맞다고 판단했습니다. 코코재팬은 제 PC에서는 접근이 되어서 PC에서만 수집합니다.

**Q. 왜 머신러닝으로 분류하지 않았나요?**
정답 라벨이 없어서 학습할 수 없고, 틀렸을 때 원인을 설명하기도 어렵습니다. 키워드 규칙은 틀리면 규칙만 고치면 됩니다. 대신 새 상품명에는 규칙을 추가해야 하는 한계가 있습니다.

**Q. 같은 상품인데 쇼핑몰마다 이름이 다르면요?**
이름 유사도로 자동으로 묶으면 표기 차이 때문에 다른 상품이 묶일 수 있어서 하지 않았습니다. 이용자가 검색한 뒤 가격순으로 직접 비교하게 했습니다.

**Q. SQL 주입을 어떻게 막았나요?**
값을 SQL 문장에 이어 붙이지 않고 물음표로 따로 전달합니다. 정렬 기준처럼 물음표를 쓸 수 없는 부분은 정해 둔 목록에서만 고르게 했습니다.

**Q. 왜 SQLite를 썼나요? 규모가 커지면요?**
서버 설치가 필요 없고 읽기 위주라서 충분했습니다. 이용자가 늘면 PostgreSQL 같은 서버형 DB로 옮겨야 합니다.

**Q. 데이터는 어떻게 최신으로 유지하나요?**
GitHub Actions로 주 1회 일요일 새벽에 자동으로 다시 수집합니다. 서버를 따로 두지 않아도 됩니다. 다만 코코재팬은 PC에서 수집해서 올려야 합니다.

**Q. 이 서비스를 공개해도 되나요?**
이용약관에 정보의 복제와 제공을 제한하는 조항이 있어서, 공개 배포는 사이트의 사전 허락이 필요하다고 보고 현재는 로컬에서 시연하고 있습니다.

**Q. 이 프로젝트에서 가장 어려웠던 점은?**
★ 지수의 경험으로 답하세요. 슬라이드의 사례 중에서는 GitHub Actions에서만 403이 나는 원인을 단계적으로 좁혀 간 과정이 가장 설명할 거리가 많습니다.

**Q. Claude Code는 어떻게 활용했나요?**
★ 지수가 답하세요. 사실대로 "어떤 부분에서 썼고, 어떤 부분은 직접 판단했는지"를 말하면 됩니다.
