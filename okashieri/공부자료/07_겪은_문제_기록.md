## 1. 코코재팬: 192건만 수집 (페이지 수 고정)
- **문제**: 수집 결과가 192건뿐. 상품이 훨씬 많아야 했음.
- **점검**: 코드의 페이지 수 고정값(8)을 의심 → 시험 수집으로 8페이지 이후 응답 확인.
- **결과**: 실제로는 88페이지까지 있었음. 고정한 8페이지까지만 수집된 것이 192건.
- **해결**: 페이지 수 고정 대신 "상품이 없거나 새 상품이 없으면 종료" 조건으로 변경. 전체 재수집 → 2,092건.

## 2. 코코재팬: BEST 상품 중복
- **문제**: 같은 상품이 여러 번 나옴.
- **점검**: 중복된 상품 위치 확인 → 페이지 상단 BEST 캐러셀이 상품 목록과 같은 class(`sct_li`)를 씀.
- **해결**: BEST 표시(`span.best_icon`)가 있는 카드 제외.

## 3. 코코재팬: 상품명 줄바꿈 → 저장 오류
- **문제**: 이미지 파일 저장 시 `OSError`.
- **원인**: 상품명 안에 줄바꿈(`\n`).
- **해결**: `.strip()`. (이후 `safe_filename`으로 금지 문자 전체 처리)

## 4. 이로이로도쿄: 198페이지까지 반복
- **문제**: 페이지가 끝없이 이어지고 같은 상품만 반복.
- **점검**: 마지막 페이지 이후 응답의 최종 주소(`res.url`) 확인.
- **결과**: 404가 아니라 **메인 페이지로 리다이렉트**(상태코드 200). 상품 목록이 아닌 메인에서 같은 카드가 반복 수집됨.
- **해결**: 응답 주소가 요청 주소와 다르면 종료 + 새 상품이 없으면 종료.

## 5. 이로이로도쿄: 빈 이미지
- **문제**: 이미지 주소가 빈 이미지(data: SVG).
- **원인**: 이미지 지연 로딩(lazy loading). 진짜 주소는 `data-src`.
- **해결**: `data-src`를 먼저 읽고 없으면 `src`.

## 6. 엔핍: 배지 이미지 약 140개
- **문제**: 일부 상품 이미지가 상품 사진이 아니라 BEST 배지.
- **점검**: 저장된 이미지를 눈으로 확인. 이미지 주소에 `/data/badge/` 포함 여부로 대상 특정.
- **결과**: 카드 안의 첫 `<img>`가 배지인 상품이 약 140개.
- **해결**: `build_db.py`가 해당 상품의 페이지에서 `og:image`를 받아 교체. 주소 해시로 캐시.

## 7. 같은 이름, 다른 상품의 이미지 덮어쓰기
- **문제**: 이미지를 상품명으로 저장하니 같은 이름의 서로 다른 상품이 한 파일을 공유.
- **해결**: 이름은 같은데 이미지 주소가 다른 상품을 찾아(`ambiguous_names`) 자기 이미지 주소로 다시 받음.

## 8. 동적 사이트에서 requests가 빈 결과
- **문제**: 엔핍에서 상품이 하나도 안 잡힘.
- **점검**: `'item-row' in res.text` → False. 같은 페이지를 Selenium으로 열어 개수 확인.
- **결과**: requests 0개 / Selenium 20개 → 자바스크립트 렌더링 사이트.
- **해결**: 엔핍만 Selenium 사용.

## 9. 재팬푸드몰 제외 (robots.txt)
- **문제**: 수집을 끝낸 뒤 robots.txt를 확인했더니 전면 금지(`Disallow: /`).
- **점검**: 접속 가능 여부(200)만 보던 기존 확인과 비교. robots.txt 직접 읽기.
- **해결**: 서비스에서 제외, 원본은 로컬에만 보관. 다음부터 수집 전에 robots.txt부터 확인.

## 14. 코코재팬 GitHub 403 — 점검 기록 (진행 중)

### 문제
GitHub Actions에서 `check_robots.py 코코재팬`이 robots.txt 응답코드 403으로 실패.

### 점검 1: 요청 내용 때문인가 (User-Agent)
PC에서 같은 주소에 User-Agent를 바꿔 가며 요청:
| User-Agent | 결과 |
|---|---|
| `Mozilla/5.0` | 200 |
| `python-requests/2.34` | 200 |
| (빈 값) | 200 |
→ 요청 내용(User-Agent)은 원인이 아님.

### 점검 2: 서버 환경 확인
응답 헤더: `Server: cloudflare`, `CF-RAY` 존재 → 코코재팬은 Cloudflare 보호 서비스 뒤에 있음.

### 추정
Cloudflare가 클라우드·데이터센터(GitHub 서버) 주소에서 오는 요청을 자동으로 봇으로 판단해 차단. **요청이 나온 장소가 원인**일 가능성.

### 한계 (확인하지 못한 것)
GitHub 쪽 403 응답의 **본문**을 기록하지 않아 Cloudflare 차단 페이지인지 확인하지 못했고, 운영자 설정은 밖에서 알 수 없음.

### 점검 3: 확인용 기록 추가 (커밋 4cd1914)
`check_robots.py`가 비정상 응답이면 `server`, `cf-ray`, `cf-mitigated`, 본문 300자를 출력하도록 수정 → Actions에서 다시 실행.

### 결과 (Actions 로그, 커밋 4cd1914 실행)
```
[확인 실패] 코코재팬: robots.txt 응답코드 403
  server: cloudflare | cf-ray: a4732cf31fa3b706-LAX | cf-mitigated: challenge
  본문: <!DOCTYPE html>...<title>Just a moment...</title>...
```
- `cf-mitigated: challenge`: Cloudflare가 요청을 **확인 절차(챌린지)** 로 막았다는 표시
- 본문 `Just a moment...`: 사람인지 확인하는 Cloudflare 대기 페이지
- `cf-ray`의 `LAX`: 요청을 받은 Cloudflare 거점이 로스앤젤레스 (GitHub 서버가 미국에 있음)
- 즉 403은 **robots.txt 규칙의 금지가 아니라 Cloudflare의 봇 확인 챌린지**였음. 실제 robots.txt 내용은 GitHub 서버에서는 읽지 못함.

### 해석
- 확정: 원인은 Cloudflare 챌린지. 요청 내용(User-Agent)이 아니라 요청이 나온 곳의 차이(PC는 통과, GitHub 서버는 챌린지).
- 추정으로 남는 부분: **왜 GitHub 서버만 챌린지 대상인지**(클라우드 서버 주소 평판 등)는 Cloudflare 내부 판단이라 밖에서 확인할 수 없음.
- 주의: 챌린지 페이지를 자동으로 통과하게 만드는 우회는 하지 않음 (사이트 운영자의 봇 차단 의사를 존중).

### 해결 (적용 중)
코코재팬은 GitHub에서 건너뛰고(워크플로 경고 `접속이 허용되지 않아 건너뜁니다`), PC에서 수집한 CSV를 저장소에 올려 사용.
(`check_robots.py`는 403을 "확인 실패"로 처리해 수집을 중단하므로 챌린지에도 안전하게 동작함.)
