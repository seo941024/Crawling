# 08. 예상 질문과 답 (소리 내어 답해 보기)

답은 "무엇을 했다"가 아니라 **"무엇과 무엇을 비교해서 왜 골랐다"** 로 말합니다. 모르는 것은 모른다고 말합니다.

## 프로젝트
**Q. 무슨 프로젝트인가요?**
일본 과자 대행구매 쇼핑몰의 상품·가격을 모아 한곳에서 검색·비교하게 하는 사이트입니다. 수집 → 정제·DB 저장 → 검색 서비스의 세 단계로 만들었습니다.

**Q. 왜 최저가를 추천하지 않나요?**
같은 상품인지 이름만으로 판별하면 표기 차이로 틀릴 수 있고, 틀리면 잘못된 최저가를 알려 주게 됩니다. 판매가순 정렬로 비교하게 하고 선택은 사용자에게 맡겼습니다.

**Q. 수집은 몇 건, 서비스는 몇 건인가요?**
원본 6,901건(5곳), 서비스 DB 5,585건(3곳)입니다. 재팬푸드몰은 robots.txt 전면 금지, 구루메상은 운영 중단·더미 상품이라 제외했습니다.

## 수집
**Q. requests와 Selenium을 어떻게 나눴나요?**
사이트마다 원본 HTML에 상품 요소가 들어 있는지 확인했습니다. 있으면 정적이라 requests + BeautifulSoup, 없으면 동적이라 Selenium입니다. 엔핍이 requests로는 0개, Selenium으로는 20개였습니다. 정적 사이트에 Selenium을 쓰면 느리고 무겁고, 동적 사이트에 requests를 쓰면 빈 데이터가 오기 때문입니다.

**Q. lxml이 뭔가요?**
BeautifulSoup이 HTML을 해석할 때 쓰는 엔진(파서)입니다. 빠르고 깨진 HTML도 잘 처리합니다. 코드의 `BeautifulSoup(html, "lxml")`이 그 지정입니다.

**Q. 마지막 페이지를 어떻게 아나요?**
고정값을 쓰지 않고 종료 조건을 씁니다. 상품이 없거나 이미 본 상품만 나오면 끝입니다. 이로이로도쿄는 404가 아니라 메인으로 이동시켜서 응답 주소가 요청 주소와 다르면 끝으로 판단합니다. 코코재팬은 고정값 8 때문에 192건만 수집한 적이 있고 실제는 88페이지였습니다.

**Q. AJAX는 어떻게 찾았나요?**
개발자도구 Network 탭에서 "더보기"를 누르고 새로 생기는 요청 주소를 찾았습니다. 응답이 HTML 조각이라 같은 파서로 처리했습니다.

**Q. 수집 중간에 실패하면 어떻게 되나요?**
임시 파일에 쓰고 끝까지 성공했을 때만 CSV를 교체합니다. 실패하면 이전 CSV가 유지됩니다.

**Q. 사이트에 부담을 주지는 않나요?**
요청 사이 2~4초 지연을 두고, 주 1회만 수집합니다.

## 허용 범위
**Q. 크롤링해도 되는지 어떻게 확인했나요?**
처음에는 접속 가능 여부(200)만 봤는데, 접속된다는 것과 수집이 허용된다는 것은 다릅니다. robots.txt를 읽어 재팬푸드몰이 전면 금지인 것을 확인하고 제외했습니다. 약관에는 정보 복제·제공 제한이 있어서 공개 배포는 허락 후에 하고, 현재는 로컬 시연 중심입니다.

**Q. 확인 순서에서 아쉬운 점은?**
robots.txt 확인을 수집 후에 했습니다. 다음에는 코드 작성 전에 가장 먼저 합니다.

**Q. robots.txt는 법적으로 강제인가요?**
법적 효력이 있는 규칙이라기보다 운영자의 의사 표시인 관례입니다. 그래서 존중하는 것을 기본으로 했습니다.

## 데이터
**Q. 왜 CSV를 거치고 바로 DB에 넣지 않았나요?**
수집은 느리고 실패할 수 있어서 정리 단계와 분리했습니다. CSV가 원본 보관 역할을 하고, 정리 규칙을 고칠 때 사이트를 다시 긁지 않아도 DB를 몇 초에 다시 만들 수 있습니다.

**Q. 분류는 어떻게 했나요? 머신러닝은 왜 안 썼나요?**
이름의 키워드 규칙으로 10개 분류에 넣었습니다. 머신러닝은 정답 라벨이 없고 오분류 원인을 설명하기 어려웠습니다. 쇼핑몰 원본 분류는 기준이 다르거나 없었습니다. 규칙은 틀리면 키워드만 고치면 됩니다. 대신 새 상품명에는 규칙 추가가 필요한 한계가 있습니다.

**Q. 분류가 틀린 적은?**
짧고 흔한 키워드(예: 이카, 아이스, 드라이)가 다른 단어의 일부로 걸려 오분류가 늘어서 삭제하고 구체적인 단어로 바꿨습니다.

**Q. 가격을 왜 숫자로 바꿨나요?**
문자열은 "10,000"이 "9,000"보다 앞에 정렬되는 등 비교가 틀리기 때문입니다.

**Q. 데이터가 맞는지 어떻게 검증했나요?**
저장된 데이터를 직접 확인했습니다. 건수가 이상해서 코코재팬 페이지 수 고정을 찾았고, 이미지를 눈으로 보다가 엔핍의 배지 이미지 약 140개를 찾았습니다.

## DB·쿼리
**Q. 저장과 호출 쿼리를 보여 주세요.**
저장은 `INSERT INTO products (...) VALUES (?, ?, ...)`, 호출은 `SELECT ... WHERE name_cho LIKE ? AND site IN (?, ?) AND sale_price <= ? ORDER BY discount_pct DESC LIMIT 40 OFFSET 0` 입니다.

**Q. `?`는 왜 쓰나요?**
값을 SQL 문장에 이어붙이지 않고 따로 전달해서, 검색어에 SQL이 섞여도 글자로만 취급되게 합니다(SQL 주입 방지). 정렬 기준은 `?`를 쓸 수 없어서 허용 목록에서만 고르게 했습니다.

**Q. 초성 검색은 어떻게 구현했나요?**
한글 음절 코드에서 초성 번호를 계산해(`(코드-0xAC00)//588`) 저장할 때 한 번 칼럼에 넣어 둡니다. 검색어가 전부 자음이면 그 칼럼에 LIKE를 합니다.

**Q. 왜 SQLite인가요?**
서버 설치가 필요 없고 읽기 위주의 수천 건 규모에 충분합니다. 이용자가 늘면 PostgreSQL 같은 서버형 DB로 옮겨야 합니다. 한계로 DB를 매번 새로 만들어서 가격 이력이 남지 않습니다.

## 서비스
**Q. REST API인가요?**
GET으로 JSON을 돌려주는 조회 API입니다. 등록·수정·삭제까지 포함한 엄격한 REST 설계는 아닙니다.

**Q. XSS는 어떻게 막았나요?**
화면에 넣을 때 `innerHTML` 대신 `textContent`를 써서 상품명을 글자로만 취급합니다.

**Q. Flask를 고른 이유는?**
화면·API 구조를 직접 설계할 수 있어서입니다. Streamlit·Gradio는 빠르지만 구조를 직접 다루기 어렵고, Django는 이 규모에 과합니다.

## 자동화
**Q. 자동 수집은 어떻게 하나요?**
GitHub Actions가 매주 일요일 새벽 3시(한국시간)에 실행합니다. 쇼핑몰별 robots.txt 확인 → 수집 → 새 DB 생성 → 상품 수 3,000건 이상 검증 → 결과물 보관 순서입니다.

**Q. PC 스케줄러나 서버 대신 Actions를 쓴 이유는?**
서버 없이 무료로 주 1회 실행할 수 있고, PC가 꺼져 있어도 됩니다. 이용자가 늘면 서버로 확장합니다.

**Q. 코코재팬은 왜 GitHub에서 수집하지 않나요?**
GitHub 서버에서만 robots.txt 요청이 403입니다. PC에서는 User-Agent를 바꿔도 모두 200이라 요청 내용이 원인이 아니었습니다. 확인용 기록을 추가해 다시 실행했더니 `cf-mitigated: challenge`와 "Just a moment..." 본문이 나와, Cloudflare의 봇 확인 챌린지임을 확인했습니다. GitHub 서버만 대상이 된 이유는 Cloudflare 내부 판단이라 확인하지 못했습니다. 우회하지 않고 코코재팬만 PC에서 수집합니다.

## 한계
**Q. 이 프로젝트의 한계는?**
서비스 범위는 3곳이고, 가격 이력은 남기지 않으며(DB를 매번 새로 생성), 같은 상품의 자동 매칭은 하지 않습니다. 공개 배포는 약관상 허락이 필요해 현재는 로컬 시연입니다.
