# 06. 자동화: GitHub Actions (`.github/workflows/weekly-crawl.yml`)

## 1. 왜 자동화가 필요한가
쇼핑몰의 가격과 상품은 계속 바뀝니다. 한 번 수집한 데이터는 시간이 지나면 낡습니다. 그래서 **매주 한 번 자동으로 다시 수집**하도록 했습니다.
- 하루 단위가 아니라 주 1회: 대상 서버에 주는 부담을 줄이고, 수집에 오래 걸리는 점(엔핍 30분 이상 등)을 감안.

## 2. GitHub Actions란
GitHub이 제공하는 **무료 자동 실행 서비스**입니다. 저장소에 "이런 순서로 실행해라"는 설정 파일(YAML)을 두면, GitHub의 가상 컴퓨터(runner)가 대신 실행해 줍니다.
- 내 PC를 켜 둘 필요 없음, 서버를 따로 빌릴 필요 없음.
- `runs-on: ubuntu-latest`: 리눅스 가상 컴퓨터에서 실행.

### 대안 비교
| 대안 | 판단 |
|---|---|
| PC 작업 스케줄러 | PC가 꺼져 있으면 실행 안 됨, PC에 의존 |
| 별도 서버(클라우드 VM) | 비용·관리 부담 |
| **GitHub Actions** | 서버 불필요, 무료 범위, 코드와 같은 곳에서 관리. 이용자가 늘면 서버로 확장 |

## 3. 워크플로 파일 해설

### 실행 시점
```yaml
on:
  schedule:
    - cron: "0 18 * * 6"      # 매주 토요일 18:00 UTC = 일요일 03:00 한국시간
  workflow_dispatch: {}        # Actions 화면에서 수동 실행 버튼
```
- cron 형식: `분 시 일 월 요일`. 시간은 **UTC**(한국 -9시간). 요일 6 = 토요일.
- `timeout-minutes: 340`: 6시간 안에 끝나야 함(GitHub 작업 제한 6시간 이내로 설정).

### 준비 단계
```yaml
- uses: actions/checkout@v4              # 저장소 코드를 가상 컴퓨터로 내려받음
- uses: actions/setup-python@v5          # 파이썬 3.10 설치, pip 캐시 사용
- run: pip install -r okashieri/requirements.txt
```

### 수집 단계 (쇼핑몰별로 robots.txt 확인 → 수집)
```yaml
- name: 코코재팬 (접속이 막히면 건너뜀)
  run: |
    if python check_robots.py 코코재팬; then
      python crawl_coco.py
    else
      echo "::warning::코코재팬은 접속이 허용되지 않아 건너뜁니다. 저장소의 기존 CSV를 사용합니다."
    fi
- name: 엔핍
  run: |
    python check_robots.py 엔핍
    python crawl_nppip.py
```
- 코드 흐름: `check_robots.py`가 성공(종료코드 0)하면 수집, 실패하면 수집하지 않음.
- 엔핍·이로이로도쿄는 확인이 실패하면 워크플로 전체가 실패(중단).
- 코코재팬만 `if/else`: GitHub 서버에서 403이 나므로 실패해도 중단하지 않고 **건너뛰고 경고만 남김**. 이때는 저장소에 올려 둔 기존 CSV를 사용하고, 코코재팬 갱신은 PC에서 수집해 올립니다.
- `::warning::`: Actions 화면에 노란 경고로 표시되는 특별한 출력 형식.

### DB 생성과 검증
```yaml
- run: python okashieri/build_db.py okashieri/okashieri_new.db      # 운영 DB와 별개로 새 DB 생성
- run: |
    python - <<'EOF'
    import sqlite3
    n = sqlite3.connect("okashieri/okashieri_new.db").execute("select count(*) from products").fetchone()[0]
    assert n >= 3000, "상품 수가 너무 적습니다. 수집이 중간에 끊겼을 수 있습니다."
    EOF
```
- 인자로 다른 경로를 주면 운영 DB(`okashieri.db`)를 건드리지 않고 **새 DB를 따로** 만듭니다.
- 상품 수가 3,000건 미만이면 `assert`가 실패 → 워크플로 실패 → **부분 수집 결과가 결과물로 올라가지 않음**. (정상은 5,000건대)

### 결과물 보관
```yaml
- uses: actions/upload-artifact@v4
  with:
    name: weekly-data
    path: okashieri/okashieri_new.db, 각 CSV
    retention-days: 30
```
- 결과를 GitHub에 **30일간 보관**(artifact). 이미지는 용량 때문에 제외.
- 자동으로 운영 DB를 교체하지는 않고, 확인 후 받아서 쓰는 구조입니다.

## 4. 실패에 대비한 설계 (겹겹이)
1. 수집 스크립트: 임시 파일에 쓰고 **성공해야 CSV 교체** (실패해도 이전 CSV 유지)
2. 상품 0개면 중단 (`SystemExit`)
3. 사이트별 robots.txt 확인 (허용되지 않으면 수집 안 함)
4. 새 DB는 별도 파일로 생성 (운영 DB 보호)
5. 상품 수 3,000건 미만이면 실패 처리

## 5. Actions 사용 팁 (실제로 겪은 것)
- **Run workflow**(새로 실행)와 **Re-run jobs**(예전 실행을 다시 돌림)는 다릅니다. Re-run은 그때의 **옛 커밋** 코드로 돌아가므로, 코드를 고친 뒤에는 반드시 Run workflow를 눌러야 합니다. 실행 기록의 커밋 해시(예: `4058f33` 옛 / `17b78c1` 새)로 구분합니다.
- 로그에서 단계를 펼쳐 출력과 오류를 볼 수 있음.
- 첫 실행은 코코재팬 robots.txt 403으로 실패 → 사이트별 확인·건너뛰기 구조로 수정 → 두 번째 실행 성공.
