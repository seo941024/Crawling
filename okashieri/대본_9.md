## 2장 1. 프로젝트 개요 (1분)

### 말할 대본
일본 과자를 직구할 때 가장 싼 곳을 찾으려면, 쇼핑몰마다 들어가서 검색하고 가격을 직접 비교해야 했습니다. 게다가 쇼핑몰마다 가격 표기와 분류 기준이 달라서 같은 상품끼리 비교하기도 어려웠습니다.

수집은 requests, BeautifulSoup, Selenium으로, 저장은 SQLite, 서비스는 Flask와 JavaScript로 만들었습니다. 매주 자동 수집은 GitHub Actions로 돌렸고, 개발할 때 Claude Code를 보조로 썼습니다.

## 3장 2. 서비스 화면 (1분, 영상)

- 카드의 가격 표시: DB에는 숫자(4900)로 저장, 화면에서 쉼표와 '원'을 붙여 "4,900원"으로 표시. 줄 그어진 가격이 정가, 옆의 %가 할인율

### 말할 대본
완성된 서비스 화면입니다. 먼저 상품 이름으로 검색하는데, 'ㅈㄹ'처럼 초성만 입력해도 찾을 수 있습니다. 다음으로 분류, 가격대, 할인율, 쇼핑몰로 조건을 좁힐 수 있고, 가격순으로 정렬하면 같은 상품이 어느 쇼핑몰에서 가장 싼지 바로 보입니다. 마음에 드는 상품을 누르면 그 쇼핑몰의 상품 페이지로 이동합니다.
지금부터 이 화면 뒤에 있는 데이터가 어떻게 만들어졌는지 설명드리겠습니다.

### 질문이 나오면

- **상품 사진은 어디서 오나?** 수집할 때 쇼핑몰 사진을 미리 내려받아 서비스 폴더에 두고, DB에는 그 파일 경로만 저장합니다. 화면은 쇼핑몰 서버가 아니라 우리 서버의 사진을 보여주기 때문에, 쇼핑몰이 사진 주소를 바꿔도 깨지지 않습니다.

## 4장 3. 데이터 파이프라인 (1분 50초)

### 이 장 이해하기
- 왼쪽에서 오른쪽으로: 수집 → 정제 → 저장·검색 서비스
- 각 칸 = 사용 기술 / 역할 / 선정 근거
- 수집 칸
  - 역할: 상품 목록 페이지 요청(requests) → 상품명·가격·이미지 추출(BeautifulSoup) / 상품이 나중에 채워지는 페이지는 브라우저를 띄워 로딩(Selenium)
  - 선정 근거: requests로 받아본 HTML에 상품이 있으면 정적 → requests, 없으면 동적 → Selenium
- 정제 칸 선정 근거: 수집·DB·웹 서버가 모두 Python이라 같은 언어로 이어서 처리, 정규식·CSV가 기본 라이브러리
  - 정규식 패턴(`[^\d]`)은 직접 작성, 적용은 Python 기본 `re` 모듈
- 저장·검색 칸 선정 근거
  - SQLite: 주 1회만 저장하고 나머지는 조회만 함 → DB 서버까지 둘 필요 없음
  - Flask: 필터 바꿀 때마다 페이지 전체를 다시 불러오지 않도록, 검색 결과만 보내는 API로 구성
- Flask = Python으로 웹 서버를 만드는 도구. "이 주소로 요청이 오면 이 함수를 실행"을 짧게 적을 수 있음 (`@app.route("/api/search")`)
- 수집과 정제를 나눈 구조: 수집은 원본 그대로 CSV에 저장 → 정제는 `build_db.py`에서 따로 → SQLite. 서비스는 CSV를 읽지 않고 DB만 사용

- 아래 "검색 서비스 구조" 흐름도: → 방향이 요청, ← 방향이 응답. 번호 순서대로 읽으면 됨
  - ① 화면 → 서버: 검색 요청 (주소 뒤에 검색어를 붙여 보냄)
  - ② 서버 → DB: Flask가 만든 SQL 조회문을 **보냄** (검색어는 SQL 명령과 분리해 값으로만)
  - ③ DB → 서버: 조건에 맞는 상품 목록을 **돌려줌**
  - ④ 서버 → 화면: JSON으로 응답
  - ⑤ 화면: 상품 카드로 출력
- 흐름도 외 설계 내용(SQL 주입 방지 등)은 질문이 나오면 답하는 용도

### 말할 대본
전체 흐름은 수집, 정제, 저장과 검색 서비스 세 단계입니다.
수집 단계에서는 먼저 requests로 상품 목록 페이지를 받아 봤습니다. 받은 HTML에 상품 정보가 있으면 그대로 requests로 수집했고, 상품 정보가 없는 사이트는 Selenium으로 브라우저를 띄워 목록이 다 그려진 뒤 수집했습니다. 수집한 내용은 가공하지 않고 원본 그대로 CSV에 저장했습니다.
정제 단계에서는 정렬이 안 되는 글자 가격을 숫자로 바꾸고, 반복 수집된 같은 상품은 하나만 남기고, 쇼핑몰마다 다른 분류를 공통 분류로 맞췄습니다. 수집부터 웹 서버까지 모두 Python이라, 정제도 같은 언어로 이어서 처리했습니다.
마지막으로 정제한 데이터를 SQLite에 저장합니다. 데이터는 일주일에 한 번만 저장하고 나머지는 조회만 하기 때문에 서버 설치가 필요 없는 SQLite로 충분했고, 필터를 바꿀 때마다 페이지 전체를 다시 불러오지 않도록 Flask는 검색 결과만 보내는 API로 만들었습니다.
아래 흐름도는 저장·검색 서비스가 실제로 어떻게 동작하는지 보여줍니다. 검색은 화면, 웹 서버, DB 세 부분이 주고받는 구조입니다. 사용자가 검색어나 필터를 바꾸면, 화면의 JavaScript가 Flask 서버에 검색 요청을 보냅니다. 서버는 그 조건으로 SQL 조회문을 만들어 SQLite에 보내고, SQLite는 조건에 맞는 상품을 돌려줍니다. 서버가 그 결과를 JSON으로 화면에 보내면, 화면은 목록 부분만 상품 카드로 다시 그립니다.
이때 사용자가 입력한 검색어는 SQL 명령과 분리해 값으로만 넘겨서, 검색창에 명령을 넣어도 실행되지 않게 했습니다.

### 질문이 나오면
- **왜 SQLite?** 데이터는 일주일에 한 번만 저장하고 그 사이에는 검색 조회만 하기 때문에, 따로 DB 서버를 설치하지 않는 파일형 DB로 충분하다고 판단했습니다.
- **왜 정제에 Python?** 수집부터 웹 서버까지 전부 Python이라 수집 결과를 같은 언어로 바로 이어서 처리할 수 있고, 정규식, CSV 읽기, SQLite 저장이 기본 라이브러리에 있어서 추가 설치가 필요 없었습니다. 매주 자동 수집 때도 수집, 정제, DB 생성을 한 언어로 연달아 실행할 수 있어 관리가 단순했습니다.
- **pandas는 왜 안 썼나?** 상품 수천 건을 한 줄씩 규칙대로 처리하는 작업이라 기본 csv 모듈로 충분했습니다.
- **Flask가 뭔가?** Python으로 웹 서버를 만드는 도구입니다. 화면에서 검색 요청이 오면 SQLite를 조회해서 결과를 JSON으로 돌려주는 역할을 했습니다.
- **왜 수집할 때 바로 정제하지 않았나?** 원본을 CSV로 남겨 두면 정제 규칙을 바꿀 때 사이트에 다시 요청하지 않고 DB만 다시 만들 수 있고, 문제가 생겼을 때 수집 단계인지 정제 단계인지 구분하기 쉽습니다. 코코재팬처럼 수집 장소가 달라도 같은 모양의 CSV만 있으면 한 번에 합칠 수 있습니다.
- **왜 머신러닝 분류가 아닌가?** 상품명 단어 규칙으로 충분히 분류됐고, 잘못 분류되면 어느 규칙 때문인지 바로 찾아 고칠 수 있어서 규칙 방식을 택했습니다.
- **SQL 주입이 뭔가?** 검색창에 SQL 명령을 넣어서 DB를 마음대로 조회하거나 바꾸는 공격입니다. 검색어를 SQL 명령과 분리해 값으로만 넘기면 명령이 아니라 그냥 글자로만 처리됩니다.
- **정렬 허용 목록은 왜?** 정렬 기준은 값으로 분리해 넘길 수 없어서 조회문에 직접 들어가기 때문에, 미리 정해 둔 정렬 기준만 받도록 했습니다.
- **textContent는 왜?** 상품명은 외부 쇼핑몰에서 가져온 글자라, 그 안에 스크립트가 섞여 있어도 실행되지 않고 글자로만 보이게 하려고 썼습니다.
- **읽기 전용 연결은 왜?** 웹 서버는 검색만 하면 되니까, 웹 요청 때문에 데이터가 바뀌거나 지워지지 않도록 DB를 읽기만 가능하게 열었습니다.
- **글자 칠 때마다 요청이 가나?** 입력이 멈추고 0.25초가 지나면 한 번만 요청합니다(디바운스). 늦게 도착한 이전 결과는 버리고 가장 최근 요청의 결과만 보여줍니다.
- **새로고침하면 조건이 사라지나?** 검색 조건을 주소 뒤에 남겨 두어서, 새로고침하거나 링크를 공유해도 같은 결과가 보입니다.
- **없는 페이지 번호를 요청하면?** 오류 대신 마지막 페이지를 보여주도록 보정했습니다.

## 5장 4. 데이터 수집 (1분 20초)

### 이 장 이해하기
- 왼쪽 표: 서비스에 들어간 3개 쇼핑몰의 사용 기술(requests = 정적, Selenium = 동적)과 다음 페이지 요청 주소. 상품 목록이 여러 페이지로 나뉘어 있어서 N(페이지 번호)을 1씩 올려 가며 요청함
  - 코코재팬 `list_more_ajax.php` = '더보기' 버튼을 누를 때 브라우저가 실제로 부르는 주소
- 왼쪽 아래 그림: 개발자도구(F12)로 상품 카드 하나의 HTML 구조를 본 것 (빨간 박스 = 상품 카드 단위, 상품명, 정가, 할인가)
  - HTML = 웹페이지의 글자 설계도. `< >` 안은 화면에 안 보이는 이름표
  - `coco2-was`(이전 가격) 이름표 → 정가, `coco2-now`(현재 가격) 이름표 → 판매가. 화면 순서가 아니라 이름표로 구분
- 오른쪽 코드: crawl_coco.py의 반복 부분
  - `seen` = 이번 실행에서 이미 모은 상품 주소 집합. 실행할 때마다 빈 집합으로 새로 시작 (지난번 CSV와 비교하지 않음)
  - 페이지마다 상품 하나하나를 `seen`과 비교 → 없는 것만 `new`로 골라 CSV에 쓰고 `seen`에 추가
  - 새 상품이 하나라도 있으면 다음 페이지로, 하나도 없으면(빈 페이지거나 마지막 페이지 반복) 종료
  - 응답코드가 200이 아니어도 종료
- CSV: 사이트마다 파일 1개. 열은 제품명, 정가, 할인가, 이미지URL, 상품링크 (이로이로도쿄만 카테고리 추가). 사이트명·할인율은 없음

### 말할 대본
수집 전에 먼저 사이트 구조를 분석했습니다. 개발자도구로 상품 카드 하나의 HTML을 열어 보고, 상품명, 정가, 할인가가 어느 위치에 있는지 확인한 뒤, 카드 단위로 정보를 뽑았습니다.
상품 목록은 여러 페이지로 나뉘어 있어서, 표처럼 주소 끝의 페이지 번호를 1씩 올려 가며 요청했습니다. 문제는 언제 멈추느냐였는데, 사이트에 따라 마지막 페이지를 넘기면 빈 페이지를 주기도 하고 마지막 페이지를 계속 다시 보여주기도 했습니다.
그래서 오른쪽 코드처럼, 이미 수집한 상품 주소를 seen이라는 집합에 모아 두고, 새 페이지에서 처음 보는 주소만 골라 저장했습니다. 처음 보는 상품이 하나도 없으면 마지막 페이지로 판단하고 멈춥니다. 이렇게 하면 빈 페이지가 오든, 같은 페이지가 반복되든 같은 기준으로 종료할 수 있습니다.

### 질문이 나오면
- **왜 상품 이름이 아니라 주소로 비교?** 이름은 비슷하거나 바뀔 수 있지만, 상품 주소는 상품마다 하나뿐이라 중복 판단 기준으로 정확합니다.
- **다시 수집하면 1페이지부터 다 겹쳐서 바로 끝나지 않나?** seen은 실행할 때마다 빈 상태로 시작하고 지난번 데이터와 비교하지 않아서, 매번 처음부터 끝까지 다시 수집합니다. 가격이 바뀐 기존 상품도 최신 가격으로 받아야 하기 때문입니다.
- **CSV에 계속 쌓이지 않나?** 쓰기 전에 seen으로 거르기 때문에 반복된 상품은 기록되지 않고, CSV는 매번 임시 파일에 새로 쓴 뒤 다 끝나면 통째로 교체합니다. 중간에 실패하면 지난 CSV가 그대로 남습니다.
- **정가와 판매가는 어떻게 구분했나?** 할인 상품은 원래 가격에 줄을 긋고 할인가를 함께 보여주는데, HTML에서 쇼핑몰이 붙인 '이전 가격', '현재 가격' 이름표로 구분했습니다. 화면 순서는 배치가 바뀌면 틀어지지만 이름표는 의미가 정해져 있습니다.
- **할인 없는 상품의 정가는?** 할인 없는 상품은 가격이 하나만 있어서 정가 칸이 비고, 정제할 때 판매가로 채워 할인율 0%로 처리했습니다.
- **엔핍은 왜 Selenium?** requests로 받은 HTML에는 상품이 없고 브라우저 화면에만 있었습니다. 페이지를 연 뒤 JavaScript가 상품을 채우는 방식이라, 브라우저를 띄워 3초 기다린 뒤 완성된 HTML을 수집했습니다.
- **이로이로도쿄는 종료 조건이 하나 더?** 없는 페이지를 요청하면 다른 주소로 자동 이동시켜서, 요청한 주소와 도착한 주소가 다르면 멈추는 조건도 넣었습니다.
- **robots.txt는?** 사이트 운영자가 자동 수집 허용 범위를 적어 두는 파일입니다. 재팬푸드몰은 전체 금지(`Disallow: /`)라 제외했고, 매주 자동 수집 직전에 허용 여부를 확인합니다.
- **요청 사이에 간격을 두나?** 짧은 간격으로 연속 요청하면 차단될 수 있어서, 요청 사이에 2~4초 간격을 두고 안정적으로 수집했습니다.

## 6장 5. 데이터 정제와 분류 (1분)

### 이 장 이해하기
- 표 한 줄 = 정제 항목 / 문제 상황 / 처리 방법
- 가격 형식: 가격이 문자열이면 크기가 아니라 맨 앞 글자부터 비교 → '1' < '9'라서 10,000원이 9,000원보다 앞에 정렬
  - '원'만 지워도 문자열 "10000"이면 똑같이 틀림 → 숫자만 남긴 뒤 정수로 변환해야 함
  - 이 작업 = 정규식(도구)으로 가격 형식을 정규화(목적)
- 중복: 두 단계로 막음
  - 저장 전에 코드가 이미 넣은 상품 주소와 비교해서 같은 주소는 건너뛰고 건수를 셈
  - DB 표에도 UNIQUE 제약(SQLite 기본 기능)을 직접 지정 → 코드가 놓쳐도 같은 쇼핑몰·같은 주소 상품이 이미 있으면 DB가 저장 거부
  - 엔핍은 같은 상품도 목록 페이지에 따라 주소 뒤 정보가 달라서, 상품 번호(it_id)만 남긴 주소로 맞춘 뒤 비교
- 과자 외 상품 제외 단어: 롬앤(화장품), 라인삭스(양말), 메쉬파우치
- 분류: 코코재팬·엔핍은 수집 데이터에 분류가 없고, 이로이로도쿄는 '쿠키스낵과자'처럼 여러 종류를 묶은 분류
  - 키워드 = 분류를 정하는 단어. 분류 10개마다 키워드 목록이 있음 (categorize.py)
  - 키워드가 하나도 없으면 이로이로도쿄의 원래 분류를 참고, 그것도 없으면 기타
- 분류 키워드 중복: "초코 쿠키" → 초코(초콜릿)와 쿠키(쿠키·디저트) 둘 다 있음 → 뒤쪽 쿠키로 분류

### 말할 대본
수집한 데이터는 그대로 비교할 수 없어서, DB에 넣기 전에 형태를 맞췄습니다.
가격이 '1,900원'처럼 문자열로 저장돼 있어서, 낮은 가격순으로 정렬하면 10,000원 상품이 9,000원 상품보다 앞에 오는 문제가 있었습니다. 그래서 숫자만 뽑아 정수로 바꿨습니다.
같은 상품이 여러 번 수집되는 문제는, 저장 전에 상품 주소를 비교해 걸러내고, DB 표에도 UNIQUE 제약을 걸어 같은 쇼핑몰의 같은 주소가 두 번 들어가지 않게 이중으로 막았습니다. 과자 쇼핑몰에서 함께 파는 화장품이나 양말은 상품명의 단어로 걸러냈습니다.
분류는 쇼핑몰마다 없거나 기준이 달라서, 분류마다 키워드 목록을 정하고 상품명에 그 키워드가 있으면 해당 분류로 넣었습니다. 예를 들어 상품명에 '젤리'가 있으면 사탕·젤리입니다. '초코 쿠키'처럼 키워드가 두 개 들어 있으면, 상품 종류는 보통 이름 끝에 오기 때문에 가장 뒤에 있는 키워드로 분류했습니다.

### 질문이 나오면
- **문자열이면 왜 정렬이 틀리나?** 문자열은 크기가 아니라 맨 앞 글자부터 한 글자씩 비교합니다. '10,000원'과 '9,000원'은 첫 글자 '1'과 '9'에서 순서가 정해져서, 만 원이 9천 원보다 앞에 옵니다.
- **숫자로 바꾼 가격은 어디에 쓰나?** 할인율 계산, 가격순 정렬, 가격대 필터에 씁니다. 화면에 보여줄 때만 다시 쉼표와 '원'을 붙입니다.
- **정규화와 정규식 차이?** 정규화는 여러 모양의 값을 한 모양으로 맞추는 목적이고, 정규식은 그때 쓴 글자 패턴 규칙입니다. 가격은 정규식으로 숫자만 뽑아 정규화했습니다.
- **UNIQUE 제약은 직접 만든 건가?** SQLite에 원래 있는 기능이고, products 표를 만들 때 쇼핑몰과 상품 주소 조합에 직접 지정했습니다.
- **왜 이중으로 막았나?** 평소에는 코드가 중복을 건너뛰고 건수를 기록합니다. DB의 UNIQUE 제약은 코드가 바뀌거나 실수가 생겨도 중복이 저장되지 않도록 데이터 쪽에서 한 번 더 보장하는 장치입니다.
- **키워드가 하나도 없으면?** 쇼핑몰이 붙인 원래 분류를 참고하고, 그것도 없으면 기타로 넣습니다.
- **키워드 위치가 같으면?** 미리 정한 분류 순서에서 앞에 있는 분류를 씁니다.

## 7장 6. SQLite DB 설계 (50초)

### 이 장 이해하기
- 칼럼 = DB 표의 열 이름 (엑셀 표의 머리글). 예: name 칼럼에는 모든 상품의 상품명이 들어 있음. 쿼리(SQL 조회문)는 이 칼럼들을 조건으로 써서 데이터를 찾는 명령
- 표 = 칼럼 묶음마다 "저장 처리(build_db.py)에서 무엇을 했나 / 조회 활용(app.py)에서 어디에 쓰나"
- 상품명은 원본 그대로(name) 화면에 보여주고, 검색은 공백 없앤 이름(name_norm)과 초성(name_cho)으로 함
- 검색용 칼럼은 검색할 때마다 계산하지 않도록 저장할 때 미리 만들어 둠
- DB 파일 이름은 코드에 `okashieri.db`로 들어 있음 (저장소와 일치시키려고 장표도 이 이름 유지)
- 아래 마지막 줄: SQLite는 DB 프로그램, SQL은 DB에 보내는 명령 언어 → 둘을 섞어 쓰지 않기

### 말할 대본
DB는 products 표 하나로 만들었고, 칼럼마다 저장할 때 무엇을 처리하고 조회할 때 어디에 쓰는지 나눠 설계했습니다.
예를 들어 가격 칼럼은 저장할 때 숫자로 바꿔 두었기 때문에, 조회할 때 가격대 필터와 가격순 정렬에 바로 쓸 수 있습니다. 검색용 칼럼에는 공백을 없앤 이름과 초성을 저장할 때 미리 계산해 두어서, 검색할 때마다 다시 계산하지 않아도 됩니다.
DB는 매주 수집 후 새로 만들고, 상품이 3,000건 미만이면 수집에 문제가 있다고 보고 기존 DB를 그대로 둡니다.

### 질문이 나오면
- **SQLite와 SQL 차이?** SQLite는 데이터를 저장하는 DB 프로그램이고, SQL은 그 DB에 "이 조건으로 찾아 달라"고 보내는 명령 언어입니다.
- **왜 3,000건?** 정상 수집이면 그보다 훨씬 많이 나오기 때문에, 그 아래면 사이트 변경이나 차단으로 수집이 덜 된 것으로 판단합니다.
- **왜 매번 새로 만드나?** 가격 비교 서비스라 모든 상품 가격을 이번 주 기준으로 맞추고, 사라진 상품도 자연스럽게 빠지게 하려고 전체를 새로 받아 교체합니다.
- **DB 정규화(표 나누기)는 했나?** 데이터가 수천 건이고 매주 통째로 새로 만들며 조회만 하는 구조라, 표를 나누지 않고 하나로 두는 게 조회가 단순하다고 판단했습니다.

## 8장 7. 문제 해결과 개선 (1분 10초)

### 이 장 이해하기
- 01 자동 수집 서버 한정 접속 차단: PC에서는 되는데 매주 자동 수집하는 서버(GitHub Actions)에서만 코코재팬이 403으로 막힘
  - 원인 분석 1: 요청 정보(User-Agent)를 바꿔도 PC 응답은 같음 → 요청 내용 문제가 아님
  - 원인 분석 2: 막힌 응답의 헤더를 기록 → `cf-mitigated: challenge` = Cloudflare가 봇인지 확인하는 절차
  - 해결: 우회하지 않음. 코코재팬만 PC에서 수집한 데이터를 쓰고, 나머지는 자동 수집 유지
- 02 한계점과 개선 과제: 한계점 → 원인 → 개선 과제 (두 줄)

### 말할 대본
수행하면서 해결한 문제 하나를 말씀드리겠습니다.
수집을 매주 자동으로 돌리려고 GitHub Actions 서버에 올렸는데, 같은 코드가 PC에서는 정상인데 이 서버에서만 코코재팬 접속이 거부됐습니다. 요청 정보를 바꿔 봐도 PC 응답은 같아서 요청 내용 문제는 아니었고, 막힌 응답의 헤더를 기록해 보니 Cloudflare라는 보안 서비스가 서버에서 온 요청을 봇으로 보고 확인 절차를 띄운 것이었습니다.
운영자가 둔 보안 장치이기 때문에 우회하지 않고, 코코재팬만 PC에서 수집한 데이터를 쓰고 나머지 쇼핑몰은 자동 수집을 유지했습니다.
한계점도 있습니다. 처음에는 마지막 페이지를 고정된 수로 가정해서, 오류 없이 끝났는데도 상품이 빠지거나 반복된 적이 있었습니다. 종료 조건과 수집 건수 검증을 처음부터 설계했어야 했습니다. 또 매주 DB를 새로 만들다 보니 가격 변동 이력이 남지 않아, 수집 날짜별로 가격을 쌓는 구조가 필요합니다.

### 질문이 나오면
- **왜 우회 안 했나?** 운영자가 자동 접근을 막으려고 둔 장치라, 우회는 사이트의 의사를 거스르는 것이라고 판단했습니다.
- **PC는 왜 괜찮았나?** Cloudflare는 요청이 어디서 왔는지도 봅니다. 같은 요청이어도 데이터센터 서버에서 오면 봇일 가능성을 높게 보고 확인 절차를 띄웁니다.
- **가격 이력을 왜 처음부터 안 남겼나?** 최신 가격 비교가 목적이라 매번 전체를 새로 받아 교체하는 구조를 택했고, 그 대가로 이력이 남지 않는 게 한계입니다.
- **수집하면서 겪은 다른 문제는?** 엔핍은 이미지 주소에 상품 사진 대신 '인기' 같은 뱃지 그림이 잡혀 있어서, 상품 페이지의 대표 이미지를 찾아 다시 받았습니다. 또 사진을 상품명으로 저장하다 보니 이름이 같은 상품끼리 사진이 덮어써져서, 그런 상품은 각자 사진 주소로 다시 받았습니다.

## 9장 감사합니다 (5초)

### 말할 대본
이상으로 오카시에리 소개를 마치겠습니다. 감사합니다.
