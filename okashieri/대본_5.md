- **크롤링(수집)**: 사람이 브라우저로 하던 이 일을 프로그램이 대신 해서, HTML 안에서 필요한 값(상품명, 가격)만 뽑아 저장하는 것입니다.

## 3장 프로젝트 개요 (1분 15초)

### 이 장 이해하기
- 예전 3장(개요)과 4장(문제 정의와 목표)을 합친 장입니다. 항목 순서: **프로젝트명 → 문제 → 목표 → 핵심 역량 → 개발환경 → 기술 스택 → 활용 도구 → GitHub**, 오른쪽은 예시 화면
- 문제의 "가격·표기·분류 기준 차이"가 뒤의 **검증·정제**로, "사이트별 개별 검색"이 **수집**과 **저장·서비스**로 이어집니다.
- **기술 스택**: 코드 안에서 직접 불러 쓰는 기술
  - requests: 사이트에 "페이지 주세요"라고 요청하고 HTML을 받아 오는 도구
  - BeautifulSoup: 받은 HTML에서 원하는 부분(상품명, 가격)만 골라내는 도구
  - Selenium: 실제 크롬 브라우저를 프로그램으로 띄워서 조종하는 도구
  - SQLite: 파일 하나로 된 작은 DB. DB는 데이터를 표 형태로 저장하고 꺼내 쓰는 창고
  - Flask: 파이썬으로 웹 서버를 만드는 도구
  - JavaScript: 브라우저 화면을 움직이는 언어
- **활용 도구**: 개발할 때 쓰는 프로그램이나 서비스
  - Git·GitHub: 코드 변경 기록 저장과 온라인 보관
  - GitHub Actions: GitHub이 정해진 시간에 코드를 대신 실행해 주는 서비스
  - Claude Code: AI 코딩 보조 도구

### 말할 대본
오카시에리는 일본 과자 대행구매 쇼핑몰의 가격을 한곳에서 비교하는 서비스입니다.
시작은 제 경험이었습니다. 쇼핑몰마다 가격과 표기, 분류 기준이 달라서, 가장 싼 곳을 찾으려면 사이트마다 같은 상품을 따로 검색해야 했습니다. 그래서 여러 쇼핑몰 상품을 한곳에서 검색하고 가격순으로 비교하는 것을 목표로, 쇼핑몰 세 곳의 상품 5천여 건을 하나의 DB로 모았습니다.
이 프로젝트에서 보여드리고 싶은 역량은 사이트 구조 분석, 데이터 검증·정제, 조회 쿼리 설계 세 가지입니다. 개발은 Windows에서 파이썬 3.10과 VS Code로 했고, 수집에 requests, BeautifulSoup, Selenium, 저장에 SQLite, 서비스에 Flask와 JavaScript를 썼습니다. 코드 관리와 예약 수집에는 GitHub과 GitHub Actions를, 개발 보조로 Claude Code를 활용했습니다.

## 4장 서비스 시연 (1분 5초, 영상)

### 이 장 이해하기
- 시연 흐름: **상품 검색(이름·초성) → 조건 필터(분류·가격대·할인율·쇼핑몰) → 가격순 정렬 → 쇼핑몰 이동**
- **JSON**: 데이터를 주고받을 때 쓰는 글 형식. 예: `{"name": "킷캣", "sale_price": 1900}`
- **API**: 화면 없이 데이터만 주는 주소. 예: `/api/search?q=킷캣` → 상품 목록이 JSON으로 옴
- **fetch**: JavaScript가 페이지를 새로 열지 않고 API에 데이터를 요청하는 기능
- 왜 나눴나? 필터를 바꿀 때마다 페이지 전체를 새로 받으면 느리고 깜빡입니다. 데이터만 받아 목록만 바꾸면 빠릅니다.
- **textContent**: 화면에 글자를 **글자로만** 넣는 방법. `innerHTML`은 HTML(코드)로 해석해서, 상품명에 `<script>`가 섞여 있으면 실행될 수 있습니다. 상품명은 남의 사이트에서 가져온 값이라 textContent를 썼습니다.

### 말할 대본
완성된 서비스를 영상으로 보여드리겠습니다.
(영상 중) 상품을 이름이나 초성으로 검색하고, 분류, 가격대, 할인율, 쇼핑몰로 좁힌 뒤 가격순으로 정렬해 쇼핑몰 간 가격을 비교합니다. 마음에 드는 상품을 누르면 해당 쇼핑몰의 상품 페이지가 새 탭으로 열립니다.
화면 구조에서는 두 가지를 신경 썼습니다. 첫째, 필터를 바꿀 때마다 페이지 전체를 다시 받으면 느리기 때문에, Flask는 상품 데이터만 JSON으로 보내고 JavaScript가 fetch로 받아 목록만 새로 그리게 했습니다. 둘째, 상품명은 외부 사이트에서 가져온 값이라 스크립트가 섞여 있으면 실행될 위험이 있어서, 글자로만 출력하는 textContent를 썼습니다.

## 5장 전체 구조와 사용 기술 (1분)

### 이 장 이해하기
- **파이프라인**: 앞 단계의 결과가 다음 단계의 재료가 되는 흐름. 상품 데이터 수집 → 데이터 검증·정제 → 저장·서비스 구현
- 단계마다 **사용 기술 → 역할(어디에 썼나) → 선정 근거(왜 골랐나)** 순서입니다. 대본은 선정 근거 위주로 말하고, 역할은 화면으로 보여 줍니다.
- 상품 데이터 = 쇼핑몰 3곳의 상품명·정가·할인가·이미지·상품 링크
- **정적 / 동적 사이트** (6장에서 자세히)
  - 정적: 서버가 상품이 이미 들어 있는 완성된 HTML을 보냄 → requests로 받으면 됨
  - 동적: 서버는 빈 틀만 보내고, 브라우저에서 JavaScript가 상품을 나중에 채움 → Selenium으로 열어야 상품이 보임
  - **렌더링**: 브라우저가 HTML과 JavaScript를 실행해서 화면을 완성하는 것
- **정답 라벨**: 머신러닝이 배우려면 "이 상품은 과자" 같은 정답이 달린 예시가 많이 필요합니다. 그게 없어서 키워드 규칙을 썼습니다.
- **예약 수집**: GitHub Actions가 매주 일요일 새벽 3시(한국 시간)에 수집 코드를 자동으로 돌립니다. 서버를 따로 둘 필요가 없습니다.

### 말할 대본
전체 구조입니다. 쇼핑몰 세 곳의 상품명, 가격, 이미지, 링크를 모으고, 비교할 수 있게 정리한 뒤, DB에 저장해 검색 서비스로 만드는 세 단계입니다. 단계마다 풀어야 할 문제가 달라서 기술도 단계별로 골랐습니다.
상품 데이터 수집은 사이트마다 상품을 보내는 방식이 달라서, 요청만으로 상품이 오는 정적 사이트는 requests와 BeautifulSoup으로, 브라우저 렌더링이 필요한 동적 사이트는 Selenium으로 나눴습니다.
데이터 검증·정제는 머신러닝을 학습시킬 정답 라벨이 없어서, 잘못 분류됐을 때 원인 규칙을 바로 찾아 고칠 수 있는 키워드 규칙을 택했습니다.
저장·서비스 구현은 서버 설치가 필요 없는 파일형 DB인 SQLite와, API 구조를 직접 설계할 수 있는 Flask를 썼습니다. 수집은 GitHub Actions로 매주 일요일 새벽에 자동 실행되게 해서, 별도 서버 없이 데이터를 갱신합니다.

## 6장 사이트별 상품 수집 방법 (1분 15초)

### 이 장 이해하기
- **판별 방법**: 같은 페이지를 requests로 한 번, Selenium(브라우저)으로 한 번 받아 상품 개수를 비교합니다. 둘이 같으면 정적, requests 쪽에 상품이 없으면 동적입니다.
- **표의 다섯 사이트**
  - 서비스에 쓰는 곳: 코코재팬, 이로이로도쿄, 엔핍
  - 수집했지만 제외: **재팬푸드몰**(robots.txt 전체 금지, 7장), **구루메상**(품절·더미 상품이 많은 사실상 운영 중단 사이트)
- **페이지 이동 방식**
  - `?page=2`처럼 주소 뒤에 번호 (엔핍, 구루메상)
  - `/page/2/`처럼 경로에 번호 (이로이로도쿄)
  - 코코재팬 '더보기' 버튼(AJAX): 페이지 이동 없이 숨은 주소로 데이터를 받아 옴. 개발자도구 네트워크 탭에서 그 주소를 찾아 직접 요청
- **왼쪽 아래 F12 캡처**: 코코재팬 상품 카드 하나의 HTML 구조. 빨간 박스는 위에서부터
  1. `li.sct_li`: 상품 카드 하나 → 코드의 `find_all('li', ...'sct_li')`가 찾는 단위
  2. `sct_txt`: 상품명
  3. `coco2-was`: 정가 (3,500원)
  4. `coco2-now`: 할인가 (1,900원)
- **오른쪽 코드 사진**: 판별 결과대로 코드를 다르게 짠 증거. 위는 requests 응답을 바로 분석, 아래는 브라우저로 열고 3초 기다린 뒤 분석합니다. 상품 카드를 찾는 마지막 줄은 두 사이트가 같습니다.
  - 정적(코코재팬): `requests` 응답을 바로 BeautifulSoup으로 분석
  - 동적(엔핍): `driver.get`으로 브라우저를 열고 `time.sleep(3)`으로 3초 기다린 뒤, 완성된 HTML(`page_source`)을 분석

### 말할 대본
수집 단계의 첫 번째 문제는 사이트마다 상품을 보내는 방식이 다르다는 점이었습니다. 서버가 완성된 HTML을 보내는 정적 사이트는 requests로 받으면 되지만, JavaScript가 상품을 나중에 채우는 동적 사이트는 requests로 받으면 빈 틀만 옵니다. 반대로 정적 사이트에 Selenium을 쓰면 브라우저를 띄우느라 느리고 무겁습니다.
그래서 같은 페이지를 두 방식으로 받아 상품 개수를 비교해 판별했고, 엔핍만 동적으로 판정해 Selenium을 썼습니다. 오른쪽 코드처럼, 코코재팬은 받은 HTML을 바로 분석하고 엔핍은 브라우저가 상품을 채울 때까지 기다린 뒤 분석했습니다.
상품은 왼쪽 아래처럼 개발자도구로 상품 카드 하나의 태그와 클래스를 분석해서, 카드 단위로 뽑고 그 안에서 상품명과 가격을 꺼냈습니다. 페이지를 넘기는 방식도 사이트마다 달라서 각각 분석했고, 코코재팬의 더보기 버튼은 네트워크 탭에서 내부 데이터 주소를 찾아 직접 요청했습니다.

### 말할 대본

## 8장 수집 중 발생한 문제와 해결 (1분 30초)

### 이 장 이해하기
- **① 코코재팬 일부 누락**
  - 수집 코드에 페이지 수를 고정해 뒀는데, 실제 페이지가 더 많아서 뒤쪽이 빠졌습니다.
  - **종료 조건**: 수집을 언제 멈출지 정하는 규칙. "새 상품이 더 안 나오면 멈춤"으로 바꿨습니다.
  - **CSV**: 표 데이터를 쉼표로 구분해 저장하는 파일. 수집 도중 실패해도 기존 CSV가 망가지지 않게, 성공했을 때만 파일을 교체했습니다.
- **② 이로이로도쿄 반복 수집**
  - **리다이렉트**: 요청한 주소 대신 다른 주소로 자동으로 보내는 것. 마지막 페이지를 넘긴 주소를 요청하면 오류(404) 대신 **메인 페이지**로 보내서 같은 상품이 계속 수집됐습니다.
  - 상태코드는 계속 200이라 오류로 알 수 없었습니다.
  - **res.url**: 실제로 도착한 주소. 요청한 주소와 다르면 끝으로 보고 멈췄습니다.
- **③ GitHub Actions에서만 403**
  - **User-Agent**: 요청에 붙는 "나는 어떤 브라우저다"라는 자기소개. 바꿔도 내 컴퓨터에서는 다 정상이라 요청 내용이 원인이 아니었습니다.
  - **응답 헤더**의 `cf-mitigated: challenge`는 **Cloudflare**(사이트 앞에서 봇을 막는 보안 서비스)가 막았다는 표시입니다.
  - 운영자가 둔 장치라 우회하지 않고, 코코재팬만 내 컴퓨터에서 수집한 데이터를 씁니다.

### 말할 대본
수집 중에 생긴 문제 세 가지와 원인을 좁힌 과정입니다.
첫째, 코코재팬 상품이 일부만 저장됐습니다. 오류 없이 끝나서 수집 범위를 의심했고, 시험 수집으로 세어 보니 실제 페이지가 제가 고정한 페이지 수보다 많았습니다. 고정값은 사이트가 바뀌면 다시 틀리므로, 새 상품이 없으면 끝나는 종료 조건으로 바꿨고, 실패해도 기존 데이터가 남도록 수집에 성공했을 때만 CSV를 교체하게 했습니다.
둘째, 이로이로도쿄에서는 같은 상품이 반복 수집됐습니다. 상태코드는 계속 200이었는데, 실제 도착한 주소를 보니 마지막 페이지 다음부터 메인 페이지로 리다이렉트되고 있었습니다. 그래서 요청한 주소와 도착한 주소가 다르면 수집을 끝내도록 했습니다.
셋째, GitHub Actions에서만 코코재팬이 403으로 막혔습니다. User-Agent를 바꿔 시험해도 제 PC에서는 모두 정상이라 요청 내용의 문제는 아니라고 보고, 차단 응답의 헤더를 기록해 확인했더니 Cloudflare의 봇 확인이었습니다. 운영자가 둔 장치라 우회하지 않고, 코코재팬만 PC에서 수집한 데이터를 씁니다.

### 질문이 나오면
- **왜 GitHub 서버만 막혔나요?** 요청 내용이 아니라 요청이 나온 곳의 차이로 보고 있지만, 정확한 이유는 규명하지 못했습니다.

## 9장 가격·분류 데이터 정리 (1분)

### 이 장 이해하기
- **가격 문자열 문제**: '1,900원'은 **글자**라서 정렬하면 '10,000원'이 '9,000원'보다 앞에 옵니다('1'이 '9'보다 작으니까). 숫자로 바꿔야 가격순 정렬과 가격대 필터가 맞습니다.
- **정규식 기반 숫자 추출**: '1,900원'에서 숫자가 아닌 것(쉼표, '원')을 지우면 1900만 남습니다.
- **UNIQUE(site, url)**: "같은 쇼핑몰의 같은 상품 주소는 한 번만 저장"하는 DB 규칙
- **키워드 분류**: 이름에 '젤리'가 있으면 사탕·젤리, '라멘'이 있으면 라면·면류처럼 단어로 분류를 붙입니다. 틀리면 어떤 단어 때문인지 바로 보입니다.
- **가장 뒤쪽 키워드 우선**: "초콜릿 커버 비스킷"처럼 상품 종류는 보통 이름 끝에 옵니다.
- **오른쪽 코드**: 위는 이름에서 가장 뒤에 나온 키워드 찾기(`rfind`는 뒤에서부터 찾기), 아래는 가격에서 숫자만 남기기

### 말할 대본
데이터 검증·정제 단계의 문제는 모은 데이터를 그대로는 비교할 수 없다는 점이었습니다. 가격은 '1,900원' 같은 글자라서 그대로 정렬하면 '10,000원'이 '9,000원'보다 앞에 옵니다. 그래서 정규식으로 숫자만 남겨 정수로 바꿨습니다. 같은 상품이 반복 저장되는 것은 쇼핑몰과 상품 주소 조합에 UNIQUE 제약을 걸어 DB에서 막았습니다.
분류는 사이트마다 없거나 기준이 달라서, 상품 이름의 키워드 규칙으로 공통 분류 10개를 붙였습니다. 머신러닝은 학습할 정답 라벨이 없고 틀린 이유를 설명하기 어려워서, 원인을 바로 찾을 수 있는 키워드 규칙을 택했습니다. 그리고 상품 종류는 이름 끝에 오는 경우가 많아서 가장 뒤에 나온 키워드를 우선 적용했습니다.

## 10장 DB 저장과 검색 기능 (55초)

### 이 장 이해하기
- **쿼리**: DB에 보내는 명령문(SQL). 예: `SELECT * FROM products WHERE name LIKE '%킷캣%'` = "이름에 킷캣이 들어간 상품 다 줘"
- **SQL 주입**: 검색어를 명령문에 **그대로 이어 붙이면**, 검색창에 `'; DROP TABLE products; --`를 넣었을 때 "상품 표를 지워라"라는 명령으로 **실행**될 수 있습니다.
  - 비유: 주문서 "메뉴: ____" 칸에 "김밥, 그리고 금고 열어 줘"라고 써서 직원이 그대로 따르는 상황
- **? 파라미터 바인딩**: 명령문에는 자리만 `?`로 비워 두고 검색어는 **따로** 넘깁니다. DB는 `?` 자리를 무조건 **값(글자)**으로만 취급합니다.
- **정렬 (ORDER BY에 ? 불가)**: 정렬 기준은 값이 아니라 명령문의 일부라서 `?`를 못 씁니다. 그래서 미리 정해 둔 목록에서만 고르게 했습니다.
- **초성 검색**: 검색할 때마다 5천 개 상품의 초성을 계산하면 느리니까, 저장할 때 한 번 계산해서 초성 칼럼에 넣어 두었습니다.
- **오른쪽 코드**: `?`로 값 넘기기, 초성 칼럼 고르기, 읽기 전용(`mode=ro`)으로 DB 열기, 정렬을 목록에서만 고르기

### 말할 대본
저장·서비스 구현 단계에서는 안전하고 빠른 검색을 신경 썼습니다. DB는 읽기 위주의 작은 규모라서 서버 설치가 필요 없는 SQLite를 골랐습니다.
조회할 때 검색어를 명령문에 그대로 이어 붙이면, 검색어에 SQL 명령을 섞어 DB를 조작하는 SQL 주입이 가능합니다. 그래서 명령문에는 물음표로 자리만 두고 검색어는 따로 전달해, 항상 값으로만 처리되게 했습니다. 정렬 기준은 물음표를 쓸 수 없는 자리라서 정해 둔 목록에서만 고르게 했고, DB도 읽기 전용으로 열었습니다.
초성 검색은 검색할 때마다 계산하면 비효율적이라, 저장할 때 한 번 계산해서 초성 칼럼에 넣어 두었습니다.

### 질문이 나오면
- **데이터가 많아지면요?** 동시에 쓰는 이용자가 많아지면 PostgreSQL 같은 서버형 DB로 옮겨야 합니다.
