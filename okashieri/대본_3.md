## 5장 서비스 시연 (1분 5초, 영상)

**[말할 대본]**
완성된 서비스를 먼저 보여드리겠습니다.
(영상 중) 상품을 이름이나 초성으로 검색하고, 분류, 가격대, 할인율, 쇼핑몰로 좁힌 뒤 가격순으로 정렬합니다. 상품을 누르면 해당 쇼핑몰의 상품 페이지가 새 탭으로 열립니다. 비교하던 목록을 그대로 유지하기 위해서입니다.
화면 구조에서 두 가지를 신경 썼습니다.
첫째, 필터나 정렬을 바꿀 때마다 페이지 전체를 다시 불러오면 느리고 화면이 깜빡입니다. 그래서 Flask는 상품 데이터만 JSON으로 보내고, JavaScript가 목록 부분만 새로 그리도록 나눴습니다.
둘째, 상품명은 외부 사이트에서 가져온 값이라 그대로 HTML로 넣으면, 상품명에 스크립트가 섞여 있을 때 실행될 수 있습니다. 그래서 innerHTML 대신 글자로만 출력하는 textContent를 썼습니다.

**[이 장에서 보여 줄 역량]** 화면을 만드는 데서 끝나지 않고 속도와 보안을 고려해 구조를 정했다.

**[알아둘 개념]**
- 흐름: 입력 → JavaScript가 fetch로 `/api/search?q=…` 요청 → Flask가 SQLite 조회 → JSON 응답(총 개수, 페이지 수, 상품 40개) → JavaScript가 상품 카드만 다시 그림
- XSS: 페이지에 끼워 넣은 스크립트가 다른 사용자의 브라우저에서 실행되는 공격. `textContent`는 값을 항상 글자로만 취급합니다.

## 7장 수집 도구 선택 (1분 10초)

**[말할 대본]**
수집 단계의 첫 번째 문제는 사이트마다 상품을 보내는 방식이 다르다는 점이었습니다.
웹사이트는 서버가 상품이 들어 있는 완성된 HTML을 보내는 정적 방식과, 빈 틀을 보낸 뒤 자바스크립트가 상품을 채우는 동적 방식이 있습니다. 동적 사이트를 requests로 받으면 빈 틀만 받게 되고, 반대로 정적 사이트에 Selenium을 쓰면 브라우저를 띄우느라 느리고 무겁습니다.
그래서 같은 페이지를 두 방식으로 받아 상품 수로 판별했습니다. 엔핍은 수집 당시 requests로는 0개, Selenium으로는 20개가 잡혀서 Selenium을 썼고, 나머지는 requests를 썼습니다.
상품 추출은 개발자도구로 상품 하나가 어떤 태그와 클래스로 되어 있는지 분석해서 그 단위로 뽑았습니다. 코코재팬의 더보기 버튼은 내부 주소로 데이터를 받는 구조라서, 네트워크 탭에서 그 주소를 찾아 직접 요청했습니다.

**[이 장에서 보여 줄 역량]** 감으로 도구를 고르지 않고 비교 실험으로 판별했다. 화면이 아니라 HTML 구조와 네트워크 요청을 분석해서 수집했다.

**[알아둘 개념]**
- 페이지 이동 방식 세 가지: URL 파라미터(`page=2`), 경로형(`/page/2/`), AJAX 더보기(내부 주소로 데이터 수신)
- **질문 대비**: 엔핍은 이후 재확인에서는 requests로도 20개가 잡혔습니다. 사이트가 바뀐 것인지 당시 조건이 달랐던 것인지는 규명하지 못했습니다. 그래서 판별을 한 번으로 끝내지 않고 같은 방법으로 다시 확인할 수 있게 정리해 두었습니다.

## 8장 수집 허용 범위 확인 (50초)

**[말할 대본]**
두 번째 문제는 수집해도 되는 사이트인지였습니다.
처음에는 상태코드 200, 즉 접속이 되는지만 봤는데, 접속과 수집 허용은 다릅니다. 운영자는 robots.txt로 크롤러의 접근 범위를 알리기 때문에, 파이썬의 can_fetch로 접근하는 주소마다 허용 여부를 코드로 확인했습니다.
확인해 보니 재팬푸드몰은 사이트 전체가 접근 거부였습니다. 이미 수집한 데이터였지만 운영자의 의사를 따라 서비스에서 제외했습니다. 이용약관에도 정보 복제·제공 제한이 있어서, 공개 배포는 허락이 필요하다고 보고 지금은 로컬에서만 시연합니다.
다만 이 확인을 수집 뒤에 한 것이 한계였습니다.

**[이 장에서 보여 줄 역량]** 기술적으로 가능한 것과 해도 되는 것을 구분하고, 그 확인을 사람 눈이 아니라 코드로 했다.

**[알아둘 개념]**
- robots.txt: `User-agent: *`는 모든 크롤러, `Disallow: /`는 사이트 전체 접근 금지. 법적 강제력은 없지만 운영자의 의사 표시입니다.
- 구루메상은 운영이 사실상 중단되어 서비스에서 제외했습니다.

## 9장 수집 종료 조건과 접근 차단 대응 (1분 30초)

**[말할 대본]**
수집 중에 생긴 문제 세 가지와 원인을 좁힌 과정입니다.
첫째, 코코재팬 상품이 일부만 저장됐습니다. 오류 없이 끝나서 수집 범위를 의심했고, 시험 수집으로 세어 보니 실제 페이지가 제가 고정한 페이지 수보다 많았습니다. 고정값은 사이트가 바뀌면 다시 틀리므로, 새 상품이 없으면 끝나는 종료 조건으로 바꿨고, 실패해도 기존 데이터가 남도록 성공했을 때만 파일을 교체하게 했습니다.
둘째, 이로이로도쿄에서는 같은 상품이 반복 수집됐습니다. 상태코드는 계속 200이었고, 응답의 최종 주소를 보니 마지막 페이지 다음부터 다른 페이지로 리다이렉트되고 있었습니다. 그래서 요청 주소와 응답 주소가 다르면 끝내도록 했습니다.
셋째, GitHub Actions에서만 코코재팬이 403으로 막혔습니다. PC에서 User-Agent를 바꿔 시험하니 모두 정상이라, 요청 내용이 아닌 다른 원인을 찾으려고 차단 응답의 헤더와 본문을 기록했고, 화면의 로그처럼 Cloudflare 봇 확인임을 확인했습니다. 자동화를 막는 장치라 우회하지 않고 코코재팬만 PC 수집본을 씁니다. GitHub 서버만 대상이 된 이유는 규명하지 못했습니다.

**[이 장에서 보여 줄 역량]** 추측으로 고치지 않고 가설을 세워 하나씩 지우며 원인을 좁혔다. 해결은 "다시 틀리지 않는 방식"으로 했다.

**[알아둘 개념]**
- 리다이렉트: 요청한 주소에서 다른 주소로 자동 이동. `res.url`이 요청 주소와 다르면 이동된 것입니다.
- Cloudflare 봇 확인: 사이트 앞단의 보안 서비스. 응답 헤더 `cf-mitigated: challenge`와 본문 "Just a moment..."가 그 표시입니다.
- `os.replace(tmp_path, csv_path)`: 임시 파일로 기존 파일을 한 번에 바꿔치기합니다. 중간에 실패하면 교체가 일어나지 않습니다.

## 10장 정제와 분류 (1분)

**[말할 대본]**
검증·정제 단계의 문제는 모은 데이터를 그대로는 비교할 수 없다는 점이었습니다.
가격은 '1,900원' 같은 문자열이라 그대로 정렬하면 '10,000원'이 '9,000원'보다 앞에 오는 식으로 순서가 틀립니다. 그래서 정규식으로 숫자만 남겨 정수로 바꿨습니다. 같은 상품이 반복 저장되는 것은 쇼핑몰과 상품 주소의 조합에 UNIQUE 제약을 걸어 DB에서 막았습니다.
분류는 사이트마다 없거나 기준이 달라서, 상품 이름의 키워드로 공통 분류 10개를 직접 붙였습니다. 머신러닝도 생각했지만 학습에 필요한 정답 라벨이 없고, 틀렸을 때 원인을 설명하기 어려웠습니다. 키워드 규칙은 틀리면 어떤 규칙 때문인지 바로 보입니다. 또 상품 종류가 이름 끝에 오는 경우가 많아서, 가장 뒤에 나온 키워드를 우선하게 했습니다.

**[이 장에서 보여 줄 역량]** 데이터의 형식 문제를 정확히 알고 처리했고, 방법을 고를 때 "설명할 수 있는가"를 기준으로 삼았다.

**[알아둘 개념]**
- 예: "초콜릿 커버 비스킷"은 뒤에 나온 '비스킷' 기준으로 쿠키·디저트 분류
- 한계: 새로운 상품명에는 규칙을 추가해야 합니다.

## 11장 저장과 조회 쿼리 (55초)

**[말할 대본]**
저장·서비스 단계에서는 안전하고 빠른 조회를 신경 썼습니다.
DB는 SQLite를 골랐습니다. 이 서비스는 읽기가 대부분이고 규모가 크지 않아서, 서버 설치가 필요 없는 SQLite로 충분하다고 판단했습니다.
검색어는 SQL 문장에 이어 붙이지 않고 물음표로 따로 전달합니다. 이어 붙이면 검색어에 SQL을 섞어 DB를 조작하는 SQL 주입이 가능하기 때문입니다. 정렬 기준은 물음표를 쓸 수 없는 자리라서, 정해 둔 허용 목록에서만 고르게 했습니다. 웹 요청이 DB를 바꾸지 못하도록 연결도 읽기 전용으로 열었습니다.
초성 검색은 검색할 때마다 계산하면 비효율적이라서, 저장할 때 한 번만 계산해 초성 칼럼에 넣어 두었습니다.

**[이 장에서 보여 줄 역량]** SQL 주입의 원리를 알고 막았으며, 계산을 언제 할지까지 설계했다.

**[알아둘 개념]**
- ORDER BY에 ?를 못 쓰는 이유: 정렬 기준은 값이 아니라 SQL 문장의 일부이기 때문입니다.
- 초성 번호 계산: `(글자코드 − 0xAC00) ÷ 588` (588 = 21 × 28)
- 한계: DB를 매번 새로 만들어서 가격 이력이 남지 않습니다. 이 내용은 12장 배운 점으로 이어집니다.

## 예상 질문과 답

**Q. 왜 정적·동적을 구분했나요?**
정적 사이트에 Selenium을 쓰면 브라우저를 띄우느라 느리고 무겁고, 동적 사이트에 requests를 쓰면 빈 틀만 받기 때문입니다. 같은 페이지를 두 방식으로 받아 비교해서 맞는 도구를 골랐습니다.

**Q. 엔핍이 동적이라고 했는데 지금은 requests로도 되던데요?**
수집 당시에는 requests로 0개가 잡혀서 Selenium을 썼고, 이후 재확인에서는 두 방식 모두 20개가 잡혔습니다. 사이트가 바뀐 것인지 당시 조건이 달랐던 것인지는 규명하지 못했습니다. 그래서 판별 방법을 같은 방식으로 다시 확인할 수 있게 정리해 두었습니다.

**Q. robots.txt는 법적으로 지켜야 하나요?**
법적 강제력은 없습니다. 하지만 운영자의 의사 표시이므로 따르는 것을 기본으로 했습니다.

**Q. Cloudflare 봇 확인을 왜 우회하지 않았나요?**
운영자가 자동화 접근을 막으려고 둔 장치라서, 우회하지 않는 것이 맞다고 판단했습니다.

**Q. 왜 머신러닝을 쓰지 않았나요?**
정답 라벨이 없고, 틀렸을 때 원인을 설명하기 어렵습니다. 키워드 규칙은 틀리면 규칙만 고치면 됩니다. 대신 새 상품명에는 규칙을 추가해야 합니다.

**Q. 같은 상품인데 쇼핑몰마다 이름이 다르면요?**
이름 유사도로 자동으로 묶으면 다른 상품이 묶일 위험이 있어서 하지 않았고, 이용자가 가격순으로 직접 비교하게 했습니다.

**Q. 왜 SQLite인가요? 규모가 커지면요?**
서버 설치가 필요 없고 읽기 위주라 충분했습니다. 동시에 쓰는 이용자가 늘면 PostgreSQL 같은 서버형 DB로 옮겨야 합니다.

**Q. 데이터는 어떻게 최신으로 유지하나요?**
GitHub Actions로 주 1회 일요일 새벽에 자동 수집합니다. 코코재팬만 봇 확인 때문에 PC에서 수집한 데이터를 씁니다.

**Q. Claude Code를 어떻게 활용했나요?**
★ 사실대로 답하세요. 예: 코드 초안 작성과 오류 원인 점검에 활용했고, 어떤 도구와 방식을 쓸지와 결과가 맞는지(수집 건수, 실제 페이지 대조)는 직접 판단하고 확인했다.

**Q. 가장 어려웠던 점은?**
★ 지수의 경험으로 답하세요. 슬라이드 사례 중에서는 GitHub Actions에서만 403이 나는 원인을 단계적으로 좁힌 과정(9장 셋째)이 설명할 거리가 가장 많습니다.
